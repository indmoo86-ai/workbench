# Workbench 总管适度主动跟进设计

日期：2026-10-12

状态：**已开发、完成四家 CLI 隔离场景验收并部署；真实项目均未启用。** 本版替代原来的小模型判断方案。当前实现为“项目群聊静默一段时间后，直接让总管检查，由总管自行判断是否需要协同”。默认静默时间为十分钟；IM 通知用户协助属于后续扩展。

## 1. 目标与原则

让总管在对话暂时停下后，主动查看有没有需要继续推动的事情，而不是要求用户每一步都点名。

不增加小模型、分类器或一套独立判断流程。程序只负责计时、排队、去重和运行一致性；是否需要协同、找谁、怎么处理，由总管判断。

总管介入不等于必须公开回复。它可以查记录、咨询相关 Agent、整理结果，也可以判断事情已经说清楚并安静结束。十分钟没有聊天，不等于进程卡死、任务失败或用户同意了某项操作。

## 2. 核心流程

```text
项目收到新的完整聊天消息
    ↓
连续十分钟没有新的有效聊天消息
    ↓
登记一次总管跟进
    ├─ 总管忙碌或暂不可用 → 合并排队，不打断现有执行
    └─ 总管可以执行 → 读取近期对话和必要任务信息
                            ↓
                  总管自行决定是否需要协同
                    ├─ 有需要 → 按原授权继续协助
                    └─ 无需要 → 安静结束，不强制回复
```

程序不再先判断“有没有协作缺口”来决定是否调用总管。是否已完成、是否正常等待、是否需要协调，都交给总管结合实际上下文判断。

## 3. 静默时间如何计算

以**当前项目群聊**为单位。默认十分钟，可在项目设置中调整。

- 从 Home 持久化最后一条有效完整消息的时间起算，不依赖各设备本地时钟。
- 用户和 Agent 的正常完整消息，包括总管正常任务的回复，都会重新起算。
- 流式文字片段、工具日志、心跳、重复投递和页面刷新不重置计时。
- 本功能产生的总管主动跟进消息及系统回执，不触发自己的下一轮静默检查。
- 空项目不触发；启用后从新消息开始，不批量补发全部历史对话的检查。

同一轮静默最多登记一次跟进。没有新的有效消息，不每十分钟重复唤醒一次。后续用户或 Agent 有新的正常交流后，才开始下一轮计时。

明确交给总管的用户请求、工具咨询和已有等待关系中的回复，仍按原机制及时处理，不额外等十分钟。已有针对同一批消息的有效续接或跟进时，复用关联，不重复创建。

## 4. 总管如何处理

跟进时给总管一条简短的当前事件，不往平台公共提示词或角色提示词里增加长篇约束：

> 项目群聊已静默约十分钟。请结合近期对话和当前任务，判断是否需要继续协同或帮助用户推进；有需要就按原授权处理，没有需要可以保持沉默。

实际文本使用配置的静默时长，并带相关消息和任务入口。该事件明确来自平台，不伪装成用户的新指令。

默认提供近期消息、必要的原始用户要求及已有运行／等待记录的简要信息；全文、其他角色及更早历史按需查询。不把全部历史、所有报告或工具日志重新注入一遍。

以下为判断示例，不是程序硬编码的分支：

| 当前情况 | 总管可以怎么做 |
| --- | --- |
| 已完成用户要求，回复也已交付 | 安静结束 |
| 某个角色仍在正常处理 | 查看必要进展，不重复派工或抢任务 |
| 审核意见已经回来，但后续讨论或汇总没人接 | 找相关角色协同，继续推进 |
| 意见冲突、信息缺失或问题无人处理 | 核对记录，咨询或协调 |
| 确实需要用户选择、补充信息或授权 | 整理清楚问题，向用户提出 |
| 运行状态不明 | 查询真实状态，不仅凭静默判断卡死 |

总管自主性保持不变，但静默触发本身不扩大用户授权，也不自动转移任务归属。原任务已取消或用户已改变要求时，不恢复旧目标；等待用户决定时，不将用户沉默当成同意。

## 5. 排队与防重复

复用现有 Home 调度、设备并发限制和总管原生会话，不增加第二个调度系统或新的业务角色。

每个项目最多保留一个未执行的本功能跟进。总管忙碌、设备离线或容量不足时保留同一个待处理项，不打断当前 CLI，不并发再启动一个总管。没有可用总管或项目暂停派发时，如实显示原因，不绕过原有限制。

实际执行前重新检查最新消息：如果已有新的有效聊天，旧的静默触发失效，按新消息重新计时。总管运行中收到用户新要求，沿用现有补充、排队或停止机制处理。

持久化记录只需关联项目、最后有效消息、到期时间和跟进请求编号。重复事件、重复调度和 Home 重启不得生成重复请求；停机期间错过的时间只合并为一次当前检查，不逐个补发。

如果总管在本次跟进中发起咨询，回复仍走现有协作和等待续接。已被该流程接收的回复不额外启动另一个静默跟进，避免“自己提问、自己收到回复、再叫醒自己”的循环。

执行异常按现有 Run 状态如实记录，不标成已完成，也不无限自动重试。同一事件的传输重试复用原编号；新一轮业务执行仍遵循现有恢复机制。

## 6. 与现有功能的关系

沿用 [总管定时任务与进度巡检设计](design-supervisor-timers.md) 的 Home 调度基础。本功能针对聊天静默，现有巡检针对运行异常；不能仅因为两者都与时间有关，就修改已有用户定时任务。

如果现有异常巡检或协作续接已经安排总管处理同一事项，合并提醒或复用待处理请求，避免重复唤醒。不同事项可以在同一轮总管跟进中列明，不能被去重误吞。

本次不调整审核计划的推进规则、业务报告结论、审批规则或角色配置。不增加固定审核顺序、强制派工或固定讨论轮数。

## 7. 设置与展示

项目设置只需提供：

- 总管主动跟进开关，建议默认关闭，由用户按项目启用。
- 无新消息的时长，默认十分钟。

不再增加小模型选择、独立判断会话、“仅观察”模式或分类结果配置。跟进直接使用总管实际派发时的配置。

执行详情保留触发时间、消息范围、排队／执行状态、结束结果及错误原因。总管安静结束时，只留后台记录，不为此额外发一条“无需介入”的群消息。

关闭开关后停止新触发，撤销尚未执行的本功能跟进，不影响普通用户任务、协作等待或已有巡检。已经开始的执行不暗中终止。

## 8. 后续 IM 通知

后续增加 IM 设置，让总管在确实需要用户协助时，通过用户配置的渠道通知用户。

通知用于需要用户补充信息、选择或授权的事项，不把每次静默检查都推送给用户。同一待确认事项应关联原任务，用户回复后沿用原任务继续处理，避免重复派工。

本轮仅记录这一扩展方向，不实现 IM 接入，不改变现有通知配置，也不发送测试通知。渠道、接收人、去重和回复接续细节留到 IM 功能设计时确认。

## 9. 验收标准

1. 有完整消息后开始计时，未达到配置时长不触发；达到时登记一次总管跟进，无小模型调用。
2. 新的正常聊天重新计时；流式日志、心跳和页面刷新不影响计时。
3. 同一静默期没有新消息，不反复调用总管；主动跟进自身不形成循环。
4. 总管忙碌或离线时只保留一个待处理项，不打断、不并发启动；恢复后按最新消息核对。
5. 计时到期与新消息、暂停、关闭开关并发时，不按失效的触发派发。
6. 重复事件、Home 重启和断线恢复后不重复生成请求，不补发历史消息风暴。
7. 直接请求和已登记的协作回复不多等十分钟，不与主动跟进重复派发。
8. 真实总管能够分别处理“已交付、正在执行、待协同、需要用户协助”场景，并能选择不公开回复。
9. 原始消息、报告、用户授权及取消状态保持有效，不因主动跟进被改写。
10. IM 在本阶段没有新增发送行为；实际执行结果与“仅登记了跟进”分别记录。

开发、测试、提交、部署和启用分别报告；真实项目启用仍由用户选择。

## 10. 当前实现与实测边界

- 项目设置提供开关和 1 至 10080 的整数分钟数，默认关闭、十分钟；旧项目不会自动启用。
- Home 的消息接收表记录首次落盘时间和不可复用的递增序号。重复消息／编辑不延长静默；启用从当前游标之后开始。
- 后台总管回合的流式输出、最终文字和无输出兜底不自动入群。需要公开时使用现有 `wb note`；`needs_input` 报告与原生审批继续保留用户入口，详细过程可在执行记录和实时现场查看。
- 跟进走正常任务、请求和会话链。已核验 CLI／设备绑定不能被刷新配置越过；排队期间修改模型和静默时长，在启动前使用最新值。
- 去重只接受明确处理关系，不把背景引用当作已经接手独立事项。同伴咨询、迟到回复及续接均保留原关系。
- 现有同工作区独占规则仍有效：同伴占用工作区时总管排队，不把跟进假定为只读而绕过限制。新完整消息到达会撤销旧的未执行检查并重新计时。
- 隔离真实 Codex 总管验证了默认十分钟触发：约 600 秒后启动，约 623 秒完成，群消息数量未增加。另验证了真实同伴咨询及原生会话续接、等待用户选择、同伴执行期间排队且不重复派工。
- 自动测试覆盖计时边界、重投、重启、设置版本冲突、跨项目隔离、排队后修改配置、失败不自动重跑和静默展示。桌面／手机浏览器验证了设置保存与重开。
- Claude Code、Grok、Agy 已分别补齐四个真实隔离场景，共 12 项、21 次正常结束的 CLI 执行：默认十分钟静默后安静结束、咨询同伴并在同一原生会话续接、向用户提出选择问题、长命令执行期间排队并在新回复后重新计时。
- 咨询校验词由同伴实际读取后返回；用户确认问题公开显示但不自动作答。忙碌场景的长命令自然结束，没有重复派工或停止命令。三家的静默项目在观察期内均只触发一次、没有额外群消息。
- 本机与服务器安装文件及 HTTP 资源逐项核对一致；只在运行和待派任务均为空时短暂暂停新派发并重载服务，随后恢复原派发状态。既有执行、原生会话、角色及任务记录保持不变，所有真实项目的开关仍为默认关闭。
- 以上是特定隔离场景的实际执行证据，不代表全部业务场景或未来每次模型判断都必然正确。未启用真实项目，也未新增 IM 接入。
