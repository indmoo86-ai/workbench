# Current Implementation Architecture

This document describes the code as it is. Product scope is defined by the [PRD](PRD.md). Capabilities that are only planned are listed under "Current limitations" and in the design documents, never here as features.

The supervisor chooses its own implementation methods and pursues missing capabilities through terminal tools, teammates or tool development before resuming the original task. It can handle authorized local work directly. Explicit user authorization may extend the instruction scope beyond the default workspace; actual runtime permissions remain enforced and require access to the specified target or an execution environment with that access. A prompt change does not expand Codex writable roots automatically. Exact previous built-in supervisor prompts follow updated defaults in either language, while custom prompts remain unchanged.

## Runtime structure

`cli-session-recovery.mjs` binds native drivers to PID/start/user and project/role/native-session proofs. Home's `cli-session-recovery-home.mjs` checks the existing task before admission and keeps unknown or busy occupancy queued. The human-only recovery dialog rechecks the displayed snapshot, stops only verified driver/tool instances and resumes the existing native association. Managed POSIX drivers have dedicated process groups; unknown orphan members block, but do not authorize signals. A deferred launch reuses its command and Run; cancellation and final admission checks prevent reactivation and slot leaks. Warm retirement reports process exit separately from finished business results. New Home/Worker negotiate `cliRecovery:1`; old Home retains conservative occupancy rejection and ordinary warm reuse. See [recovery contract and measured coverage](design-cli-session-recovery.md).

Optional bilingual role templates describe responsibilities for planning, execution, review, testing, architecture, debugging, deployment and documentation. Template execution prompts are empty, and existing role definitions are not migrated; stable template keys remain separate from localized names. User-saved instructions are not bulk-edited. On the new `minimalInstructions:1` Home/Worker path, normal execution contains trusted role identity, saved custom instructions, the current task and necessary task events, not a default planning/review sequence. Responsibility remains discovery data, not the owner's execution prompt. Exact previous maintained platform/supervisor defaults normalize to concise bilingual defaults; custom values, including explicit empty values, remain unchanged. This path is released on compatible macOS and Linux Workers; optional saved-source synchronization is a separate capability and input contract. The isolated adapter-specific evidence and post-rollout acceptance limits are maintained in [the design](design-minimal-injection.md#11-observed-acceptance-boundary).

The CLI chooses whether and how to collaborate. Explicit user authorization may extend the instruction scope beyond the default workspace; actual runtime permissions remain enforced. A prompt change does not expand Codex writable roots automatically. Essential isolation boundaries and repositories outside the current directory remain disclosed; ordinary device and repository inventories are queried on demand.

The editable supervisor template in `minimal.supervisorTemplate` covers goals, requirements, team coordination, evidence-based follow-up and unified delivery. It respects named assignments and independent reviews, refers to actual remaining quota proportions among suitable members and counts a shared account's quota once. It adds no quota allocator, mandatory team query or new dispatch policy. Work-role templates remain responsibility-only with empty execution prompts; the saved supervisor text is a separate component frozen at next-turn admission. An explicit clear stays empty, and changing UI language does not translate user-saved text.

### Managed input language

The sidebar mode selector uses adjacent Group chats / Sessions buttons with a highlighted pressed state and left/right keyboard switching. It shares the existing native-session mode transition and binds the compose icon to the currently selected mode.

The separate native Sessions view (`public/native-sessions.js`) is a human-only browser entry, not an Agent tool or collaboration session. Its default catalogue uses persistent titled `nativeCatalogEntries` created by the shared dialog, not arbitrary native histories. Home and Worker retain the entry identity separately from the exact vendor session ID; Home can return cached entries while a device is offline. Explicit group filtering uses managed session IDs, while device filtering separates independent histories from those group sessions. Native-session capability 2 prevents older Workers from ignoring these scopes. Operations/focus and a visible-page-only timer refresh the catalogue, with coalesced refreshes and preserved selection/scroll position. Terminal launch still uses the existing private Worker environment, claim identity and iTerm/SSH command builder. Bound project folders retain the project reservation; standalone folders use a terminal-only scope reconciled by the same background return mechanism. No model or managed Run is created for preview, and native terminals receive no platform/role instructions. See [native browser contract and acceptance](design-native-session-browser.md).

The role terminal entry displays `latestTerminalRun` as a summary rather than a history selector. Its new-session action calls the same native form with only device/runtime defaults, leaving the folder and native permissions to the user. Historical resume still uses the Run terminal endpoint; an existing claim retains its actual Run binding and release/stop controls. No history is deleted and the standalone action does not use the group-bound fresh-role terminal endpoint.

The separate browser module `public/output-language.js` converts prose display copies from Traditional to Simplified Chinese without translating English. `room.js` applies it to chat, quotations and attachment Markdown; `document.js` applies it to document Markdown; `app.js` applies it to execution text/results. The UI translation walker also normalizes Chinese prose, excluding raw, code and editable containers. Quotations and mixed Latin/Chinese prose are converted, while code, commands, resource paths and link destinations are protected. Original/history views, copy sources, persisted events and model-facing input are unchanged. The browser uses the pinned `opencc-js` 1.4.2 `t2cn` ESM distribution under `public/vendor/`, registered in Home static assets and the service-worker cache.

`input-language.mjs` separates execution-template language from UI localization. Maintained identity, instruction replacement/revocation and runtime wrapping text uses the English catalog. `executionInstructionComponents` converts only the send copies of custom prose before calculating actual component fingerprints; saved configuration versions remain independently recorded. `createRunInput` converts dynamic task prose once and logs that same copy handed to the adapter. Prepared instruction components and configuration events are not converted again, preserving trusted role names and matching native instruction parameters.

The local `opencc-js` dictionary uses standard Simplified-to-Traditional conversion without a model request or native binary. Code fences, indented code, known command/code lines, executable paths, identifiers and exact quoted strings retain their originals. Ambiguous bare ASCII executables followed by Chinese text also retain the whole line rather than risk renaming an argument; this can preserve mixed prose such as an ASCII product name followed by Chinese. Marking code explicitly gives unambiguous protection. Trusted roster and source-author names are quoted before the send copy is converted. All four managed adapters use this path for initial input, retained-process continuation and exact-session resume. UI language changes alone do not invalidate instruction fingerprints. Existing native history, tool results, attachments and direct manual terminal input are outside this transformation. The background organizer uses English maintained templates but preserves its original structured material and UTF-16 coverage ranges; its source material is not a managed-dialogue send copy. Rolling installation keeps the existing Home/Worker protocol; devices running older Workers retain their old behavior and must be upgraded before this policy is claimed for them. Saved user-authored platform, supervisor and role prompts are not automatically translated to English.

Role history is a tab in the ordinary role editor and the supervisor settings; cards retain only the terminal action. Clearing history archives and marks that role's platform sessions, removes their native-session associations, and hides its previous runs from terminal candidates. The next dispatch creates a new platform/native session. Shared project chat, code files, other roles and audit records remain intact. The authenticated clear endpoint checks the expected current session and rejects unfinished work, CLI switches and terminal takeover, including takeover of historical runs on previous devices. Cleared session IDs cannot be read through session tools or resumed through the terminal endpoint. This is a fresh start, not recovery of missing vendor history.

Role configuration supports persisted, reversible CLI switching on the same device. Codex and Grok perform an original-session handoff, verify a staged successor and commit the binding only after process settlement; cancellation before commit keeps the original binding. Claude and Antigravity switching remains explicitly unavailable until its native maintenance path is verified. See [design-role-cli-switch.md](design-role-cli-switch.md) for the supported scope and acceptance boundary.

Git delivery help is local and never submits a request. Delivery arguments are validated before contacting Home. For project-scoped Runs without a legacy role repository URL, an explicit SHA may use the sole repository captured on that Run; multiple repositories require the existing `auto`/items form. Approval and fixed-commit publication remain separate from updating a target checkout, and uncommitted files are not included. Supervisor guidance distinguishes a Git-hosting ref from the actual version in a device's bound directory.

### Shared role instructions

`agent-calls.mjs` atomically accepts one or more role targets through the existing calls endpoint. The CLI repeats `--role`; the endpoint accepts a `roles` array or the legacy `role` string. One room message owns the common text and recipient snapshots, while `coordinationRequests` retain separate stable IDs, provenance, limits and execution state. All recipients validate in one transaction; same-ID replay checks the target set and content. Single-role IDs and the compatibility `ask` identity remain unchanged. `callMessageId` keeps direct results, notes and continuations linked to the shared instruction. Session receipts bind every addressed request, including several requests routed to one supervisor, and cannot create a second broadcast driver. Explicit execution order still belongs to the schedule API.

Sent cards represent message acceptance, not receiver completion: the sender's card is completed once registered, without recipient counts. Each receiver has an independent live reply/progress view. Quoted previews are projected from same-project visible source messages and open the original viewer; no text-based historical merging or persisted-text rewrite occurs. Card footer actions remain local to the card.

### Source synchronization boundary

Pending-command and batch queries use dedicated SQLite partial indexes before materializing command bodies. Scheduling and write-busy checks read only matching pending commands; receipt and capture queries read the requested batch. Historical records and their manifests remain stored unchanged, with the existing receipt, retry, cancellation and conflict rules.

Home validates already-uploaded apply receipts before accepting a later transient transfer error. Only a committed result receives an acknowledgment tied to its content hash; Worker removes only the matching outbox receipt. Completed command replay restores a missing receipt without reapplying files. Upgrade Home before Workers: new Workers retain receipts when an older Home sends an unbound acknowledgment. After asynchronous credential reads, dispatch rechecks pause, connection identity, current command/run ownership and source/terminal locks before sending a launch.

Project-file synchronization is an opt-in capability separate from browser state deltas and fixed-commit Git delivery. Home stores manifests, acknowledgements, conflict ownership and content staging; Workers exchange only missing changed-file content over the authenticated connection. Directory capture policy 3 adds filesystem baselines with `baseCommit: null`, explicit project/repository scope partitioning and a bound `displayNodeId`; legacy Git capture policy 2 remains supported. `source-sync-watch.mjs` persists observations and unacknowledged notices, combines eligible-directory notifications with 30-second reconciliation and feeds the existing queue. Pause and active-writer gates still fence applies. Scope preview/activation and compatible Workers are required.

Directory snapshots capture at most eight files concurrently after scoped enumeration. Every capture still reads and hashes stable current bytes; it does not reuse a prior manifest or trust modification time. The first capture error stops new work and drains in-flight captures before rejection. Existing content-addressed blobs are read and verified before attempting creation; identical in-flight saves join within one process, with no completed-verification cache. Before managed CLI input, the provenance tracker records monotonic elapsed time, scope count, captured-file count and unavailable scopes in the Run's `preparationScan` event and a localized execution log. This measurement covers file verification, not queue wait, native CLI startup or model response time. Failed scopes still supply no modification-attribution evidence, and warm CLI reuse and synchronization conflict rules remain unchanged.

`project-files.mjs` maps authorized references by registered scope ID and relative path to the selected Mac; `project-file-read.mjs` reads its actual files through Worker queries. Viewing is independent of sync activation: saved display identity takes precedence, or a unique bound Mac is discovered (ambiguous devices require selection). Current read bindings include registered baseline and read-only repositories, not arbitrary isolated worktrees; write-sync bindings remain separately restricted. Shared `.workbench/docs/` content uses the same file engine. Recent Outputs uses bounded Run/tool evidence, not the whole inventory, and distinguishes successful writes from citations. Paths are confirmed by the Mac; descriptor-verified modification time is display metadata, never conflict resolution or author evidence. Availability, disabled/pending transfer, conflicts and read errors remain explicit. There is no browser-specific content copy. An isolated Run's relative links remain relative to its own workspace. Conflicts retain both versions; evidence-bound modifiers receive a repair task, and independently accepted candidates are rechecked at every endpoint. Directory transfer is not a Git delivery receipt. Legacy pinned Git overlays remain on their own contract; isolated outputs must first be delivered into project directories. See [the contract and measured acceptance limits](design-source-sync.md); software installation does not activate other business scopes.

### Cross-device state and reliable delivery

`http-response.mjs` negotiates asynchronous gzip for buffered static text and authenticated state/chat reads of at least 1 KiB, with `Vary: Accept-Encoding` and the encoded content length. State/chat keep `no-store`; public assets keep `no-cache`. Clients excluding gzip receive unchanged bytes. SSE, WebSockets, credential endpoints and attachments do not use this path. Page, favicon and touch-icon references use the existing 192px derivative rather than downloading the 512px image for small UI elements; PWA installation retains its declared icon sizes. Service-worker installation excludes the large optional 512px and legacy Codex images from eager precaching; they remain available for network-first caching on actual use. This reduces transfers through SSH without extending request timeouts or changing dispatch.

The Home remains the only owner of project state and messages. Local and remote Workers use the same authenticated WebSocket protocol; they differ only in the network path. Web SSE is an update hint and not a durable message queue; a reconnecting browser pulls authoritative state from the Home.

`GET /api/state?view=workspace&projectId=...&cursor=...` is projected by `workspace-state.mjs`. It returns the tasks, runs, calls, discussions and plan metadata of the current project while keeping global configuration and navigation. Bodies do not enter this hot state and the original database is not trimmed. `/api/tasks/:id/detail` also covers tasks that have not started, `/api/runs/:id/detail` returns the original Run and Task, and events and files are read through the existing interfaces. The cursor contains a process generation and a projection hash. Four versions are kept per project, with at most sixteen project caches; when a baseline is invalid or the Home restarted, a full lightweight snapshot is returned. The front end applies additions, deletions, changes and ordering against the baseline, and a generation counter isolates late responses when switching projects. The original `/api/state` is kept for compatibility. SSE hints for token and tool events are merged to about 100 ms, and critical state is announced immediately.

The paginated Room messages read adds display-only `dialogue` names to saved directed questions and final-reply messages. `Rooms.messageDialogue` follows same-project, same-recipient continuation ancestry back to the original call and resolves its sender, with cycle detection. It does not create messages, expose unpublished Run results or rewrite saved content/timestamps. The browser shows sender → recipient in the existing bubble header, with a wrapping header on narrow screens and no separate collaboration-state panel. Question Original links read the message itself.

The execution-details Result original tab reuses `history-view.js` inline, following Artifacts. The selected Run ID—not a request's latest continuation—anchors its versioned history reads. Its reader survives tab/state rerenders, invalidates pending pages when the Run changes or the dialog closes, and copies raw stored text without display conversion. Execution-result cards no longer open a separate original dialog; ordinary message/quote viewers remain message-bound.

`message-progress.mjs` derives the displayed stages from the original command, request and Run. A command record stores the first and last send, the count and the acknowledgement time, and a Run records when it was actually received and the time of terminal events. A Worker acknowledgement does not mean the CLI has processed it, and creating a continuation does not mean the continuation has started; business acceptance stays independent. If a run is known to have ended but its call was not wrapped up, only the existing finish is called and the business work is not executed again.

The Home dispatches serially per node. An unacknowledged command is resent with the same ID at intervals of at least 5 seconds. The task input and the platform prompt of the first launch are fixed into the command, so configuration changes do not alter a retransmitted input. The Worker outbox is written to the database before sending and is replayed in per-Run `seq` order. The unacknowledged window holds at most 64 events or about 256 KiB; one oversized event can be sent alone, still subject to the WebSocket frame limit. Retries reuse the original ID and never skip a same-Run event that temporarily does not fit. After reconnect reconciliation a `ready` message is sent. Deleting a project keeps a body-free `deletedRuns` ownership tombstone and acknowledges late events only to the original node, so that an old queue cannot block all new tasks. An unknown Run that cannot be verified is kept and reported as an error and is not silently dropped.

After a short network drop, an idle session that is still alive gets a 30-second grace period; its fingerprint and idle deadline continue to apply, and an explicit pause or exit closes it immediately. This keep-alive does not revive dead processes and does not guarantee continuity of model context.

Retained CLI processes keep their immutable OS environment. For Agy, Worker sets `WB_REQUIRE_TURN=1` and supplies `wb --turn RUN_ID` for each turn. The CLI resolves only that run's bridge under the inherited workspace and validates its run, role-session, conversation, workspace and bridge identities. Missing, expired or mismatched selections fail before operations; there is no latest-turn lookup or mutable shared pointer that could promote an old background command. The existing five-minute warm retention remains unchanged. Help and unknown-command discovery do not require a live context; Codex/Claude/Grok retain their existing explicit-context invocation. A successful report acknowledges persistence, not process completion, and does not force-stop the CLI.

`wb call --file` reads a caller-selected, realpath-validated UTF-8 file inside its bound workspace/project/repositories. It preserves the text in JSON reference data with byte length and SHA256 before the existing call API, identity validation and idempotency checks. Binary, out-of-scope and over-limit payloads fail without submission or truncation. Protected independent-review turns reject this shortcut and retain the original guarded document APIs. No additional document store, synchronization rule or persistent prompt is introduced.

### Read-only team queries for project roles

`wb setup catalog` is open to all roles of the current project. It returns peer responsibilities, CLI/model bindings and project directories. Ordinary callers do not receive peer execution prompts; the supervisor retains peer prompts for existing management workflows. Own responsibility is excluded from both the role catalog and team roster, including duplicated role entries in configuration proposals. `wb discuss peers` applies the same caller-relative boundary without requiring discussion preview. Disabled, offline, unconfigured and active archived roles remain distinguishable. Reading a directory grants no additional write permission.

`wb discuss peers` requests a compact project directory: stable identities, peer responsibilities, enabled/configured/archived state, device and availability, observation time, directory version and completeness. Offline/disabled members remain present; archive inclusion and detailed configuration are explicit options. Query failure is not an empty team. Sender/project fields are rejected; the Worker bridge binds a trusted active Run and Home derives its identity. Old Workers retain their legacy detailed directory and launch-time input contract. On the new path the roster is not injected, and latest saved instructions are frozen separately at actual Worker admission without rewriting historical task/role snapshots.

`execution-configuration.mjs` freezes independently versioned components for the admitted turn. A running turn stays immutable; queued edits apply at actual start. Fetch/start/resume failures are recorded without a stale fallback or model-confirmation round. Current Run/tool environment updates independently. Codex keeps the process and native ID but releases a settled loaded-thread subscription before reloading current environment; it uses native developer instructions plus a one-time changed/cleared-component developer event through `thread/inject_items`. An acknowledged append is not repeated merely because the later model turn fails. Claude retires changed idle processes and resumes the same session with appended instructions; Grok reads current rules per resumed process. Both also deliver operator-approved one-time replacement/revocation messages when components change. Agy appends such messages to its original session, suppressing unchanged components. Native/global CLI configuration is untouched. Old message/history rules are not erased; Agy's old-rule interference and context cost are explicitly accepted.

Role definitions are edited independently in the existing UI. Authenticated `PATCH /api/projects/:projectId/roles/:roleId/definition` requires the current revision and accepts only responsibility/instructions for ordinary active roles; it does not probe Workers, create tasks or alter bindings. Full saves and older proposals preserve an omitted responsibility; explicit empty clears it. The supervisor has a built-in outward duty and keeps the existing prompt editor. Templates provide independent defaults; custom text is not translated on language changes.

The minimal platform text identifies Workbench and its short help entry; it does not force team queries or cooperation. `wb note` notifies, `wb call` consults or delegates, and sending does not automatically wait. `wb wait` explicitly registers dependencies and ends a dependent turn. `discuss ask/reply` requires targets supporting discussion v2; the preview is not enabled automatically. General duties locate collaborators rather than imposing functional limits. Explicit user assignments, reviews and approvals remain binding.

Reviewer default duties and maintained prompt examples distinguish independent findings from assigned repair/re-review. They do not infer authorship from a developer role name. The on-demand scheduling guidance asks the supervisor to state the independent-review handoff when assigning a batch, while preserving factual consultation. New-role presets continue to have empty instructions; existing user prompts are not silently migrated. Explicit configuration edits use the current revision and apply at the next actual dispatch without resetting native history or altering an already frozen turn.

### Three-column workspace and recent artifacts

Role context occupancy is a separate `context_usage` event persisted as `run.contextUsage`, leaving cumulative `usage` unchanged. Claude pairs the last main-conversation assistant/message-start input (fresh + cache creation + cache read) with the exact model's native `modelUsage.contextWindow`; result totals and child-agent requests are not context measurements. Codex uses `tokenUsage.last.inputTokens` (cached input already included) and `modelContextWindow`. Compaction invalidates the previous count until another measurement. `public/context-usage.js` selects only the current primary role session on the configured device/runtime/model, and renders a hollow used-percentage ring with measurement time. Missing telemetry/limits, including older Runs and current Grok/Agy streams, remain unknown. The existing state refresh transports updates without starting any model or modifying sessions; no automatic/manual compaction action is added by this display feature.

Terminal process reconciliation runs every 15 seconds and on Worker readiness after startup/reconnect, without a browser or model turn; Home never infers remote PID state itself. The workspace refresh and role-status refresh use the same project-level check. Automatic and manual calls are deduplicated separately so a manual revocation is not swallowed by a background grace period. Home asks Workers advertising `terminalControl:1`, retains offline/unsupported/unknown claims, and consumes released receipts before continuing the original queue. Workers advertising `terminalAutoReturn:1` retain unopened prepared links for 5 minutes during automatic checks; manual refresh can revoke them immediately. Home delays automatic checks of older Workers and in-flight preparation until the same grace expires. Active/dead process checks do not wait for this grace, and automatic checks never send signals. Worker inspection and link revocation share a SQLite transaction with native claiming, including tombstones for preparation still in flight. New native launchers record owner/start identities for wrapper and CLI; old live records require a recognizable launcher or direct child. The terminal dialog's human-only stop action is bound to the saved claim, not supplied PIDs. It signals verified descendants, waits after TERM, escalates to KILL if needed, and releases only after verified exit. Concurrent stop requests share the pending operation; stopping claims still consume capacity. Late launcher completion or preparation cannot reopen a released claim. This does not reset role/native history or terminate other sessions.

Plan badges and stage labels derive activity from current coordination requests, continuation requests and Runs instead of treating an open scheduler stage as active execution. Queued tasks show their blocking reason. Actual starting/running Runs override an old task queue reason; waiting for a reply or user input remains distinct. This changes display only, not plan acceptance or scheduling.

Project Settings places its basic-information save inside that section; it persists only the existing name, description and legacy repository URL fields. Folder binding, device-folder preparation and repository preparation keep their independent endpoints and show feedback next to the corresponding action. The supervisor card opens a separate Role Details dialog using the same field layout and settings/history tabs as ordinary roles. Its existing supervisor configuration endpoint, fixed identity, built-in responsibility, shared supervisor prompt and CLI-switch protocol are retained; the dialog contains no project configuration controls. Important actions retain their icons with visible English/Chinese labels, using an opt-in marker rather than changing other toolbar buttons. Editing a section clears its previous result. Project deletion is isolated in a danger section and retains the existing confirmation. The project file sync entry uses the same name in settings, Resources and its dialog; its protocol and activation rules are unchanged. Styles are scoped to these project controls.

Codex runtime avatars use the black OpenAI Blossom from the [official brand assets](https://openai.com/brand/). Role-card frames are 30px; chat frames remain 36px. Proportional SVG scaling reduces internal blank space without clipping the mark. Other runtime icons, the application logo, role names and runtime bindings are unchanged.

The role sidebar pins the project's existing fixed supervisor above its work roles. Authenticated state exposes these records in `supervisorRoles`, separate from the ordinary role catalog and excluding the platform assistant. Its blue title displays “Supervisor” / “总管” for the selected language without a duplicate system-role label; this is a display name, not a stored identity change. Custom work-role names remain untranslated. The card reuses status, quota, terminal and history controls; editing opens the existing project supervisor configuration instead of the work-role editor. The sidebar refresh includes both kinds of roles without creating or dispatching tasks.

Project settings no longer bind a fixed planner. At startup the coordinator removes legacy `plannerRoleId` fields and increments the coordination revision once, without deleting roles or rewriting task/run history; old clients cannot restore the retired binding. Supervisor conventions require selecting collaborators from current responsibilities and availability for each task. The redundant project intake selector and separate dispatch-save button are removed; the supervisor run-device setting remains the single visible entry. Existing backend routing records are preserved. The project settings page also previews the shared default supervisor prompt and links to the existing global editor. Its prompt-only mode saves just `supervisorPrompt`, preserving platform prompts and model defaults; restoring defaults remains an unsaved draft until explicitly saved. The scope is all projects and later supervisor turns, not a per-project prompt override.

Cloud device icons in role cards carry small, centered numbers inside the cloud outline, in Home's persisted device registration order, including offline devices. All roles on the same device share a number across projects and refreshes; local device icons remain unnumbered. Tooltips and accessible labels include the number and device name. These are display numbers, not device IDs; removing/re-registering devices can change their ordering.

The supervisor reasoning-effort control is a dropdown driven by the selected device's CLI/model catalog, with an explicit CLI-default option. Switching the model retains a supported choice or clears an unsupported draft choice; an unavailable saved value stays visible with a warning until explicitly changed, so refreshing settings does not silently rewrite saved configuration.

Claude model effort capabilities are read through a bounded native initialization control request with session persistence, hooks and MCP startup disabled, without sending a user turn. The existing model selection catalog and provider-specific identity stay intact; only recognized levels explicitly advertised for the matching alias or resolved provider ID enter the UI. Capability detection runs alongside the existing quota check, and unavailable metadata leaves levels unspecified without disabling an otherwise authenticated CLI. These are CLI capability declarations, not measured backend reasoning budgets. Selecting a level uses the existing `--effort` execution parameter; an unspecified value leaves the CLI default untouched.

The resource panel's upper shortcuts still show online devices only; its lower list includes offline registered devices. Clicking a local shortcut, local device row or local role-card machine icon opens the selected project's bound directory in Finder on that macOS Worker. The authenticated Home endpoint resolves the project/device binding, not a browser-supplied path, and forwards it only to a local Worker advertising `openProjectFolder:1`. The Worker rechecks its permitted roots and the canonical directory before invoking Finder. Missing bindings, offline/older Workers and unsupported platforms return explicit errors. This does not open a directory on the browser's device when the browser is elsewhere, start a CLI task, change role identity or alter cloud remote-desktop behavior.

The global Basic Settings tab combines language, browser API Token, WeChat and remote execution controls. The former `connection` tab identifier normalizes to `general`, so existing entry points continue to open the combined panel. Its heading, tabs and content share the same centered width and symmetric scrollbar gutter; only the tab bar sticks to the top during scrolling. Pages without the global tabs retain their sticky heading. Dialog IDs and backend settings remain unchanged; only the navigation and grouping change.

`public/browser-token.js` shares the Home access token between the workspace and standalone document viewer through origin-scoped `localStorage`. Legacy `sessionStorage` tokens migrate on load. Saving verifies the candidate with Home before replacing the stored value; invalid candidates or failed storage writes leave the dialog open. Other workspace tabs pick up storage changes and reconnect. The token is not embedded in static assets or returned by an unauthenticated endpoint. This is persistent browser storage, not encrypted credential storage: only use trusted browser profiles, and clearing site data or changing origin/profile requires setup again. Home authentication remains enforced.

The project navigation buttons are excluded from automatic DOM translation because their titles and accessible labels contain user-supplied names; repository counts inside them are translated explicitly when rendered. The shared top heading opts out only when displaying a project name, while settings headings and the empty-state label remain translatable. This avoids treating a project named after a UI label as interface text.

The three tabs at the bottom right use line icons for roles, files and resources with no button text, and keep title and aria-label text, a selected state and keyboard switching, shared by desktop and mobile. The brand, project and right-column headers share a light blue-white background (`#f0f5fc`) and a subtle lower shadow; the color applies to headers only.

Projects use ten built-in shapes and colors from `role-icons.js`. They are assigned by project ID and persisted in the current browser's localStorage; renaming, reordering and refreshing do not change an existing identity. A new project prefers an unused icon and beyond ten they are reused evenly. The cache is not synchronized across devices. When the desktop sidebar is collapsed a 44 px column of clickable project icons remains, with `title`/`aria-label` for the full name and `aria-current` plus a blue bar marking the current project. The mobile drawer still shows icons and text.

`workspace-inspector.js` maintains the right-column tabs, file details and the desktop divider. Widths are stored in localStorage and constrained by the available screen width; the 90vw mobile drawer does not affect the desktop width. The top bar is a uniform 54 px, and the desktop bottom bars are fixed at 67 px to align with the single-line input; when the input grows only the middle area grows upward. The role, recent artifacts and resource panels scroll independently, and the header title and actions follow the tab. Online devices, local/cloud shortcuts, device management and Git sync are collected in the resources tab.

`GET /api/projects/:id/artifacts` is implemented by `run-artifacts.mjs`. From the latest 40 Runs that have a workspace it collects successful write-tool records and Markdown file links in replies. The same path on the same device is de-duplicated, the workspace is not scanned as a whole, and not every file is claimed to be produced in this turn. There are at most 100 candidates and 12 source Runs, metadata is requested from Workers over four concurrent paths, and anything beyond that is explicitly marked partial. The Worker's `artifact_files` reads file stat after realpath, workspace-boundary and sensitive-path checks; only ordinary paths and `.workbench/docs` are allowed. Evidence of a write comes from Codex completed-tool events, Claude `tool_result` and the existing Antigravity completion status; a call intent or a reference cannot stand in for a successful write. If the file mtime does not match the recorded write-completion time the modifier is left empty, and a referrer is never passed off as the author. Edits outside the platform and missing history cannot be inferred.

The front end loads on demand, reuses the latest query for 30 seconds, and invalidates late responses when the project is switched or the detail is closed. File details use the existing Run document/file interfaces and Markdown is rendered with safe DOM; files that cannot be previewed still show metadata and the reason. When the device is offline or an old Worker has no metadata capability, the source is kept and no modification time is fabricated. The PWA static cache includes the new module, while API responses and file contents are never cached.

### Peer discussion preview (off by default, unreleased)

`RoleDiscussions` reuses the Home records and SQLite transactions and maintains discussion topics, full messages, deliveries, idempotent actions and recovery intents; it adds no business RoleCalls edges. `wb discuss peers/ask/reply/read/resolve` enter `/api/agent/discussions` through the file bridge of the current Run, and the Home verifies permissions from the real Run. Web replies and an explicit "handled" mark go through separate project discussion interfaces; cancelling a wait is never inferred from ordinary message text.

The `task`, `clarification` and `answer_resume` turns are separate. A discussion Run uses the receiving role's own native session and workspace and does not overwrite the original Task owner or `currentRunId`. After the current question is acknowledged and the consuming turn has ended safely, a unique intent resumes the original business Task. It does not resume early while an old child call is unfinished. Rooms schedule capacity and bounded priority uniformly; a redirection cancels information waits and resolved-but-unstarted continuation intents.

Question rounds and directions are validated separately; an answer to an old Q1 cannot release Q2. A topic gets three questions by default and a root task six, and the allowance can be raised in a controlled way by the fixed supervisor or the user. A missed answer is recorded as `failed/no_response` and is never replayed automatically: ordinary tools may change things and a successful exit does not prove there were no side effects. An unknown process keeps its lock and `reconciling`, and is not cancelled by the 300-second process reclaim or the two-hour wait.

Weak prompt-based coordination is used: dedicated discussion sandboxes, temporary directory limits, disabling external tools and per-purpose operation allow-lists were removed, and each CLI keeps its normal execution parameters. The turn purpose and the bridge directory do not change the warm-process fingerprint. The preview is deliberately narrow: `WB_DISCUSSION_PREVIEW=1` additionally requires a match in `WB_DISCUSSION_VALIDATED_CONFIGS` for the actual absolute binary path, probed version and model. If it is missing or does not match, the preview stays off. A runtime refresh updates capabilities.

`discussionTargetStatus` is shared by team reachability, accepting a new ask and the actual delivery check. It rejects offline targets, unknown connections, unavailable logins, expired probes, a missing model and unverified configurations. A rejected new question creates no wait and consumes no budget; if the target is lost after saving, the original question and the waiting reason are kept. `discussionSupported` means support is declared and `discussionReady` means a new question can be sent in this turn. For a started turn, read/reply/resolve continue to finish under the frozen identity, question, direction and stop state, and answers are not discarded because of later probe withdrawal.

When a CLI wrapper changes `HOME`, a matching session directory must be provided explicitly. A wrapper that keeps its history in a separate account directory otherwise blocks answer consumption through the default path. Setting `CLAUDE_CONFIG_DIR` fixes new session records. The code does not search other accounts and does not create blank sessions to pretend to resume.

Managed roles receive a convention through `executionRules` and `discussionInstructions`: query peers before editing, check `git status/diff`, declare files with `wb note`, and talk first when files overlap. A new Worker declares an independent `peerStatus=1`; an old Worker and tasks without a role session get only Git and manual coordination hints. `wb discuss peers` does not depend on the preview switch. It returns same-project tasks, Run state, the actual workspace and repositories reported by the Worker, and the three most recent note excerpts with full-text IDs; directories that have not started are marked pending/planned. It is not a file lock and cannot discover unmanaged CLIs.

The Home's static asset allow-list includes the PWA manifest, the Service Worker and the app icons. The Service Worker intercepts only same-origin static GETs, tries the network first and falls back to the page cache on failure. `/api/`, the Worker WebSocket, dynamic documents and credentials never enter the offline cache. Desktop installation is managed by the browser, and the Home and Worker remain independent background processes.

### Human queue steering

`POST /api/projects/:projectId/tasks/:taskId/steer` only promotes a human group-chat Task that has not started. `RoleSteering` fixes the `commandId`, the list of Runs to stop and the related plan within a synchronous SQLite transaction, cancels the old call tree of the target and persists the stop command; the original message text is not rewritten. The original role session lock is released by the Worker's terminal event, and the new Run reuses the exact native ID. `steeringWaitReason` blocks early dispatch in both Rooms and Store, and a queued steering message takes precedence over ordinary continuations. Clicking again or a network retry does not create another message.

Old call ancestors are marked with `steeringTaskId`, which prevents a late result from waking the old supervisor chain. The related plan is blocked and its unexecuted members are cancelled, while active sibling roles are not stopped. A remote plan query re-checks the steering marker after it returns. The prompt marks a user redirection separately and treats history as background only; side effects that already happened are not rolled back. The UI uses the Home's `capabilities.roleSteering` to distinguish upgraded services.

Role editing is managed by `public/room.js`. The form keeps only the role's own configuration, while project directory validation still affects whether it can be saved.

### Long-lived project baseline branch

- A project first gets a stable directory. For every associated Git repository, the Worker creates `.worktrees/project-baseline/<key>` inside the project from the remote source branch or a specified full SHA. All devices use the same `agentwb/<projectId>` branch and fixed commit. A remote collaboration branch is created by default; a read-only reference repository can opt out explicitly. The source clone is not switched. `repositoryWorkspaces` points to the baseline worktree, and roles and later Runs inherit that path.
- Supervisor stages still run in a short-lived worktree per Run. After a passing verdict with a clean version, the Worker fast-forwards only the descendant commits of repositories that were declared writable into the source device's project baseline. Cross-device delivery follows the existing approval; on publish the remote project collaboration branch is fast-forwarded as well, and the receiving device verifies the fixed SHA and fast-forwards its own project baseline. A repository without changes takes objects from the original source branch and creates no delivery ref. A non-fast-forward, a dirty directory or a version mismatch stops the sync, and the main line is never advanced automatically.
- The Git version panel queries each repository on each device. The project summary counts unique repositories, and commit differences aggregate across device copies. Offline devices and unpublished collaboration branches are marked separately, and the version of one device is not taken as the version of the whole project.

### Cross-device attachment transfer

- `Attachments` is still the only source of project attachments. `AttachmentTransfers` uses the existing Worker query to determine the target directory from the project binding and creates no Task or Run. `POST /api/projects/:id/attachment-transfers` takes a client idempotency ID, a node and an attachment ID. Duplicate in-flight requests are merged, a failure can be retried explicitly with the same ID, and a success returns the original receipt. An offline device is not silently replaced by another.
- The Worker declares `attachmentTransfer=1`. `attachments_receive` and the automatic download of a Run share `receiveAttachments`, and files land in `.workbench/tmp/attachments/<transferId or runId>/`. Each directory level is checked against escaping the workspace, the size and SHA-256 are verified, and a temporary file is renamed atomically. The extension is kept and the display name is separate from the on-disk name. A standalone download is allowed only for the Worker credential and the attachment set currently being transferred.
- The Home stores `attachmentTransfers` receipts so the UI can show the path. A Run reports the actual paths through the `attachmentFiles` state, and role prompts inject those paths. Temporary files are not cleaned automatically, are not mixed into Git delivery, and no additional file sync service is introduced.

### Supervisor silence follow-up

`proactive-followup.mjs` is called by the existing Home scheduling tick, not an independent scheduler or classifier. Project settings persist `proactiveFollowups` with an opt-in switch, integer silence duration (1–10080 minutes, default 10), revision and message cursor. `room_message_receipts` supplies immutable first-write Home timestamps and monotonic SQLite receipt sequence numbers; enabling snapshots the current tail, so old chats are not replayed. Explicit follow-up provenance is resolved through stored Task/Run/request/discussion links. Monitor tasks expose their exact message references for deduplication, without changing their schedules or anomaly policy.

Due events atomically create one internal platform message plus an ordinary Task and coordination Request. Before `Store.startTask` claims a Run, the event's message anchor, switch and duration are checked again. New normal messages and disabling withdraw unstarted initial turns only; active turns and dependency continuations keep their original relationship. The supervisor uses its current saved configuration and normal role-session/capacity/workspace locks. Errors and waiting reasons remain attached to the real Task/Request/Run.

Background supervisor Runs retain their input and output for details and the read-only live scene, but do not create a normal streaming chat bubble or an automatic completion message. Explicit `wb note` remains public; `needs_input` reports and native approvals retain their user-facing entry points. A platform event and bounded recent excerpts supply context without expanding shared prompts; full history remains on demand. No IM integration is added. See `design-supervisor-proactive-followup.md` for the feature contract.

### Native terminal lifecycle

The role terminal picker defaults to the latest resumable Run and shows only that entry plus New session. Runs without valid native IDs and cleared histories are omitted; an existing takeover keeps its original binding. This is a display filter only: stored executions, input/output events and native transcripts are not deleted, and the role-history tab retains its existing records.

`public/live-scene.js` provides an independent read-only dialog from role cards and message actions. It reads authenticated Run detail and pages the existing events endpoint with `after` and optional `limit` (1–1000); paged responses include `hasMore` and a small `runState` snapshot. Legacy requests retain their original response shape. Viewing never sends terminal preparation, resume, stop or dispatch operations. Initial reads and incremental polling reconnect; closing cancels browser reads only. Generation checks isolate project/Run switches. Unchanged DOM is preserved while output arrives and manual scrolling pauses following.

The scene presents the actual saved input snapshot, output and tool lifecycle records, not hidden native instructions or reasoning. Stable tool IDs merge streamed deltas and final snapshots. Codex command deltas and completed tool results, Claude/Grok tool results, and Agy step updates retain bounded output with explicit truncation flags. A native summary remains a summary: Agy `view_file` can expose only line/byte counts, and the viewer does not reread a file to manufacture the missing result. Historical unrecorded input/results cannot be recovered by opening the viewer.

The role-card terminal entry defaults to **New session**, including after history was cleared or before any Run exists. Authenticated `POST /api/projects/:projectId/roles/:roleId/terminal` prepares/releases a manual native terminal with a stable operation ID. It resolves the current role device, model and bound project directory; no historical Run or native ID is fabricated. Shared and role execution prompts are supplied, but the owner's responsibility is not injected. The native user/environment remains private on Worker. This terminal does not replace the role's managed session mapping or send its conversation back to the project chat; managed `wb` tools remain unavailable.

Cloud terminal dialogs show the registered SSH destination and explicitly offer **Open new session via SSH**, **Resume via SSH**, and **Copy SSH command**. New sessions and historical resumes both use the existing `ssh -t` launcher with that device's host/port/user, switching to the Worker user when different. The browser-side terminal must be able to reach and authenticate to the server; a stored Home password is never embedded in a command or URL. Missing server registrations do not fall back to running locally.

`terminalLaunchView` percent-encodes the command for the iTerm URL rather than using form-encoded `+` spaces. New preparations, repeated prepare responses and state snapshots all use this view, so previously saved incorrect links are corrected on read without changing command text, lease IDs, native history or takeover locks.

Worker capability `terminalFresh:1` gates new-session preparation. Role/CLI switching, active or unreconciled processes, node capacity and project takeover locks are checked again after asynchronous directory validation. Released requests are tombstoned; late prepare replies cannot recreate their locks, and a successful return rotates the dialog operation ID for the next fresh session. New wrapper launches recheck the canonical directory. Existing past Runs remain selectable and continue through the exact-native-ID resume endpoint unchanged. Closing the dialog alone does not release an already prepared terminal: use **Return to platform** after its CLI exits.

- Run events support incremental reads with `after` sequence numbers. `public/room.js` de-duplicates streaming increments and completion snapshots, a fullscreen view is bound to project/task/run and keeps the body after completion, and scrolling up manually pauses following. The full text is kept.
- The adapter stores `nativeSessionId`, and the Worker adds the original user, CLI path and session storage environment. The original CLI environment, including authentication and proxy settings, is stored only in the Worker's `runtimeEnvironments`, never sent back in status events, and excludes WB and platform credentials.
- `src/terminal-resume.mjs` defines four resume commands, history verification, the project-node takeover lock and the interactive wrapper. `prepare` of `POST /api/runs/:id/terminal` reserves the lock on the Home, and the Worker then verifies that the original process has exited, the original directory and the vendor history. An iTerm command URL starts the wrapper; SSH uses the registered host and switches to the original Worker user if necessary. Old executions without an environment record are refused.
- The wrapper and the release use Worker SQLite write transactions to coordinate. A prepared ID can be claimed only once, and on release it is atomically checked that the wrapper and child process have exited. Project deletion, queue dispatch, Worker start and managed Git publication are all protected by the takeover lock. The lock survives Home and Worker restarts and is not released automatically when the device is offline or the state is uncertain. New conversation in the terminal does not flow back to the group chat, the `wb` bridge is not restored automatically, and processes started manually by others are not covered by this lock.

### Per-device CLI capacity

Device details expose a shared CLI limit (integer 1–64) through authenticated `POST /api/workers/:nodeId/capacity`. Home persists it in `workerConfigs`; the Worker persists its applied value separately and advertises `cliCapacity:1`. Active/preparing role runs, retained idle processes, background organizers and prepared/active terminal takeovers share the device limit. Short-lived, no-inference runtime discovery probes and manually started external CLIs are not managed execution slots.

Home queues tasks by device capacity. Worker independently reserves slots before asynchronous launch preparation and defers a full-device launch without acknowledging or failing it; retransmission keeps the same command, immutable input and role/native-session IDs. Cancelling a deferred launch records a settled interruption, so a late delivery cannot revive it. `capacity_state` wakes pending work without triggering another quota probe. Lowering the limit never interrupts admitted runs; they drain first. Idle processes are reclaimed oldest first, and their actual exit is awaited before replacement. With spare capacity an eligible role reuses its live process; after retirement it resumes the exact persisted native session, and unsupported keep-alive adapters continue through their existing native resume path.

Saved offline limits remain pending and are applied on reconnect before `ready`. Older Workers cannot apply this protocol and must be upgraded before an online edit; Home never allocates them above their reported concurrency. Folder/name edits preserve the saved limit. Manual terminal preparation reserves capacity on Home before Worker verification, but a full device returns a clear wait error instead of opening another CLI.

### Collaboration efficiency increments

`public/execution-progress.js` is the shared read-only execution-progress projection used by Home message progress and browser chat, role, plan-member and task-detail displays. It maps existing records into six display states (`queued/running/waiting/completed/stopped/error`), with transport phases, waiting reasons and timestamps retained as details. No parallel persistent state machine is introduced. Unknown processes remain waiting for reconciliation; cancellation does not imply process exit. Compact workspace snapshots omit reply bodies and cannot by themselves establish an empty response. Historical Runs and peer-discussion turns do not inherit the current task's waits or acceptance.

`RoleCalls.finish` records a normally completed delivery as `succeeded`, independently of the report verdict; an empty consultation without a substantive final answer or report is an `incomplete_output` delivery failure. `outcomeFor` reads only the saved report, otherwise `unverified`, rather than manufacturing a negative verdict from a process error. Dependency waits, continuation identity and cancellation fences are unchanged. Existing execution-plan stop/report policies retain their previous admission conditions explicitly after this separation; the change adds no review order, automatic rework or approval policy. Old terminal records are not migrated or retried, and the UI uses available execution evidence without rewriting those records. Verdicts are displayed in the delivery report, not in execution-progress badges.

`consultRound` remains historical continuation metadata, not an admission quota: schedule completion and replies from different reviewers must not consume a shared three-round allowance. RoleCalls retains its root limit of twenty non-continuation requests, depth/cycle checks, idempotency and cancelled-parent validation. No old requests or reports are rewritten when this check changes.

Dispatch pause permits a narrow read/settlement allowlist for already running identities (reports, notes, waits, context reads and existing discussion replies/resolution). Worker bridge and Home enforce the same allowlist; stopping, reconciling, disconnected and ended runs cannot send. New consultation/schedule/delivery operations remain blocked. Reports reject exact probe placeholders without claiming to semantically validate evidence. Print tool results retain up to 12,000 characters of output independently of assistant text; process success still does not prove a business verdict was accepted.

- `src/run-reports.mjs` receives the structured verdicts `passed/failed/blocked/needs_input` of an active Run. Exit status and business verdict are stored separately. By default, stages of `executionPlans.requiresReports` advance only with a passing verdict and a complete version; old history is not forcibly migrated to "passed". The one optional exception is `failurePolicy:collect_reviews` for a purely independent review batch: every member must have `purpose=audit` and declare no repository writes, and the supervisor rules require independent reviews to form their own batch and select this policy explicitly. `runFailureKind` classifies the error of a failed Run as `temporary_service`, `incomplete_output`, `authorization` or `unknown`. The coordination request stores the classification and the original error and propagates them through continuations. Only a confirmed-ended `temporary_service`, `incomplete_output` and an explicit negative opinion continue collecting. Insufficient quota (including 429) is not treated as ordinary rate limiting; authorization or unknown errors, cancellation, needing an answer, an unknown execution result, a missing explicit verdict, or an abnormal isolated version still block. Earlier members' opinions are not injected, the Git baseline is not advanced, and a finished batch with `completed_with_issues` does not mean passed. The interface still defaults to stop; it does not retry automatically or switch models. The evidence in `wb report` is a claim by the role and still needs real verification.
- `src/cli-print-session.mjs` keeps CLI error reasons and partial text. Antigravity `step_update` and `tool_info` are merged by `conversation_id + step_index` into tool start and completion records, and an explicit final SUCCESS can override an intermediate diagnostic. RoleCalls stores the true `runStatus` and propagates it through continuations. Supervisor summaries distinguish execution failures from negative opinions, and steps not executed keep `notExecutedReason`.
- Platform, project, role and per-assignment content is injected in layers. `platform-prompts.executionRules` defines the execution boundary uniformly. The Worker writes the hand-off automatically. A new group-chat Run carries a fixed `contextPacket` with the original instruction, the conversation summary or clearly marked excerpts of uncovered content, and source IDs. Result continuations can look up the original text by ID.
- `src/history.mjs` provides search and paging over messages, Runs and calls of the same project. A `runId` returns that turn's original text, a `requestId` follows the continuation chain to the final report, and later pages carry `version` to prevent mixed reads. `wb history search/read` and `wb result read` use the existing file bridge, with the Worker forwarding to the Home. `public/history-view.js` provides loading the next segment and copying the full text. Tool logs are not mixed into the report.
- Before starting an execution the Worker checks `wb capabilities protocol=2` and declares `collaborationTools=2`; an old Worker does not receive new report tasks. All CLIs use the same `wb`, with no vendor plug-ins or new service.
- Persistent role sessions: `roleSessions` stores, per project conversation and role, the default session, native ID, node, runtime, working directory and the Run holding the lock; each turn still creates its own Run. The Home claims the session inside the dispatch transaction, and the Worker verifies the original user, storage environment, history file and directory before resuming with the specified ID. A mismatched native ID, missing history or a previous turn in unknown state all refuse a blank continuation. Codex uses `thread/resume`; Claude, Grok and Antigravity use non-interactive resume parameters. The Worker releases the session lock after confirming the turn is complete and the tools of this turn are cleaned up. Processes that support keep-alive enter an idle pool, and human takeover still uses the project device lock.
- `conversationContexts`, `summaryJobs` and `summaryQueues` store summaries, batches and the background queue per project conversation. Ordinary group-chat speech or an actual dispatch registers the queue. The Home dispatches business work first and then uses spare capacity of the organizer device to process a batch; the whole Home has at most one organizer query in flight. A Worker receives new batches only if it declares `summaryBatches=1`. On Workers with `cliCapacity=1`, an admitted organizer finishes without being preempted; subsequent business work waits for its slot. The separate model configuration in base settings is unchanged, and the worker-role `wb` credentials are not passed.
- The organizer processes in original order, with at most 20 messages per batch, a 10000 UTF-16 character body budget and at most 20000 characters of serialized input. A single long message is split by whole code points, and `partialThrough` stores the message ID, a body fingerprint and the offset read. `coveredThroughMessageId` advances only after a message has been read completely. Results keep real sources and reject stale versions and overlong outputs. On failure the old summary is kept with 60-second and 300-second back-off, and after three consecutive failures it waits for new messages or a configuration change; business preemption does not count as a failure. A Home restart marks unconfirmed batches `interrupted` and continues from the accepted cursor.
- `startTask` reads the actual summary and the full range of messages at that moment in one transaction and freezes them into `contextPacket`. Uncovered body text has a 12000-character budget, favors recent human messages and allows at most 1000 characters per item. The directory lists at most 100 items, the number and range beyond that are saved explicitly, and omission is never treated as having read. An excerpt provides the original length, a body hash and the `wb history read` entry. `wb chat summary` returns the actual coverage, the organizer state and a paged directory of all uncovered items, and a change of directory version rejects mixed page reads. An explicit quote is limited to 8000 bytes and also has a full-text entry. A late summary does not change an old Run, and a retransmitted command uses its original snapshot.
- `wb session current/list/summary/read` and `wb chat summary` use the same file bridge. They query only the assignments, replies and summaries visible on the platform for the current project and conversation, and do not claim to read hidden CLI reasoning. The role card can show paged original text and explicitly start a new session while keeping old history.
- `src/scheduled-jobs.mjs` stores project schedules and trigger records. Ordinary dispatch supports once, interval, daily and weekly with an interval of at least 15 minutes; a progress patrol supports only interval, at least 10 minutes. `src/timer-monitor.mjs` reads only the run alerts of the current project and the latest execution plan. With no new anomaly it only updates the checkpoint; a new anomaly merges into one supervisor dispatch, and a recurrence after recovery can notify again. Due jobs reuse Room/Task/Run, are de-duplicated by `jobId + dueAt`, unfinished child chains block re-entry, missed runs merge, and offline roles are not switched. `src/timer-agent.mjs` restricts `wb timer` to the fixed supervisor identity of an active Run, de-duplicates by `requestId` inside a SQLite transaction, rejects stale edits by `revision` and keeps an audit record. All CLIs reuse the same Worker file bridge, and without `timerTools=1` the new tool is not announced.
- Role permissions on one device still cover the whole project. An execution plan can use `repositories` to limit the set of repositories prepared in this run. When an object is missing across devices, a pending approval delivery is registered; after approval the fixed ref is fetched into the target object store and the original stage continues after the SHA is confirmed. The target's original branch is not switched and a push is never approved automatically.
- `src/run-monitor.mjs` performs a model-free check every minute. A device going offline or 10 minutes without a run event produces one visible notice that clears on recovery. Silence is not judged as success or failure, and processes are neither killed nor re-dispatched on its own.

Timers are executed by the current Home. A Home on a sleeping laptop cannot dispatch on time.

### Main modules

- `src/home.mjs` provides the web UI, REST, SSE and the authenticated Worker WebSocket through Node HTTP.
- `src/worker.mjs` is an independent process that connects out to the Home and registers local capabilities, commands and events. Before starting a runtime it fixes the working instruction and the prompt of this turn through `src/run-input.mjs` and sends one `input` event.
- `src/store.mjs` stores tasks, Runs, commands and events with SQLite transactions. The Home and the Worker use different files.
- `src/attachments.mjs` manages project attachment upload, type detection, authorized download and the Worker's SHA-256 check; browser file names are never used as storage paths. `public/room.js` manages per-project attachment drafts and previews.
- `src/execution-plans.mjs` handles supervisor-approved stage plans, reuses the `waiting_dependencies` state of `coordinationRequests` and releases stages after the parent turn completes. `src/execution-workspace.mjs` fixes repository versions and creates multi-repository worktrees per Run. The Home and the Worker both validate the project lock, batch and capacity.
- `src/rooms.mjs` stores project roles and group chat, parses the user's explicit `@`, creates internal dispatches, queues by role and node capacity, and posts the terminal result back to the chat once.
- Explicit set dispatch freezes `schedulingTargets` (IDs) and `schedulingRoster` (names at send time) in `Rooms.post`, only for the supervisor entry. Natural language recognizes only explicit "all roles" or "review roles" sentence patterns and never infers dispatch from quotes, code, summaries or existing opinion roundups. The `contextPacket` of a Run carries the fixed roster separately, and the original instruction is not rewritten. `ExecutionPlans.submit` checks for omissions before creating calls and returns the role names. At most 12 participants by default, the same as the existing scheduling limit. A role card prefers the real Run state and the corresponding call wait state, so that an old `Task.blocked` and `waitingReason` do not pose as the current failure, and `Store.event` clears waiting reasons on a terminal state.
- `src/project-setup.mjs` manages supervisor validation, project configuration proposals and the direct update of worker-role prompts in the current project. `src/project-admin.mjs` unifies project operations from the page and from the AI. `src/project-space.mjs` computes directory and snapshots of all repositories, and `src/setup-workspace.mjs` performs clone and check on the Worker.
- `src/device-admin.mjs` checks and onboards devices over SSH, and the Home manages the reverse SSH tunnel of cloud Workers: after the child process exits it retries every 5 seconds. The server's sshd should enable a 30-second interval and 3 keep-alive probes for unresponsive clients to clear stale sessions that hold the remote forwarded port after a network drop. `src/hosting.mjs` calls the official GitHub and Gitee account and repository-creation interfaces, with credentials stored in a private file in the Home data directory; `src/platform-assistant.mjs` reuses the CLI and configuration cards and creates no new model service.
- `src/agent-bridge.mjs` bridges CLI requests inside the workspace of this turn, and the Worker forwards to the allow-listed agent interfaces. The CLI sandbox does not need network access, approval configuration and arbitrary URLs are not exposed. Temporary communication files are cleaned at the end of each turn and there is no offline replay.
- `src/folders.mjs` lists directories inside the allowed scope on the Worker side, with canonical path validation against escaping, and `src/repository.mjs` validates credential-free GitHub/Gitee HTTPS and SSH URLs uniformly.
- `src/codex.mjs` uses App Server JSONL. `src/cli-print-session.mjs` supports bidirectional `stream-json` multi-turn sessions for Claude and Antigravity, while Grok keeps single-turn print plus exact-ID resume. The Worker's `warm-sessions` cache processes of finished turns by role session and configuration fingerprint, and idle processes exit after 300 seconds. Active capacity and the idle cache are separate with a default combined limit of 4. A Run's terminal state is published after the turn completes and the tool bridge is cleaned up, and keep-alive does not use an active slot. Cancel, pause, disconnect, terminal takeover and configuration mismatch first confirm the release of the old process, and an unknown leftover PID refuses a second resume.
- `src/turn-context.mjs` generates tool context for each turn's separate bridge directory, and `wb-cli` loads the turn prefix specified by the prompt at startup. The file is cleaned with the bridge, so a background command from the previous turn cannot get the next turn's identity through shared context.
- A same-project `consult` is delivered by the Home directly to the target role, and across devices it does not go through the supervisor model. A consultation inherits neither the source execution permission nor a file snapshot. After results are collected, the `RoleCalls` continuation is reused and returns to the asker along the request ID. Rooms run one turn per role, a continuation goes first once and then ordinary FIFO resumes, and a discussion has at most three consultation rounds. The Worker's `warm_sessions` report the actual idle processes, and the front end shows "CLI ready" only when the device is online and not expired.
- `public/app.js` manages projects and nodes, the independent settings pages and the conversation log. The conversation detail fixes the task title, creation time and state at the top, and the body scrolls in a single container. `public/run-log-data.js` groups and incrementally de-duplicates input, streamed text and real tool calls. The artifacts tab reuses the report, Git delivery and workspace-file interfaces, and old Runs do not fake missing full input. `public/room.js` provides the group chat, role settings, quoted replies and history paging. Updates use SSE and degrade to bounded polling on token authentication or connection errors.
- The primary UI color is bright blue `#0866ff` with `#004bcc` for dark interactions and light blue or white backgrounds. The `accent` variables in `public/styles.css` unify primary buttons, selected states and function icons, and success, warning and error keep their semantic colors. The double-terminal logo has a solid deeper-blue tile and staggered white terminals spanning approximately 85% of the icon width. It uses `assets/app-icon.png` as its raster source; `public/app-icon.png` (512) and `app-icon-192.png` (192) are resized derivatives used by the page, favicon and PWA. The old SVG is retained as a historical asset, not the current generation source. Versioned icon URLs and the service-worker cache version change together when replacing the logo.
- `public/plan-dock.js` selects the latest `executionPlan` of the current project by creation time and derives the current step and member completion from the coordination requests. It does not trust a model's self-reported percentage and does not prefer an older running plan. The plan card sits just above the input box, is collapsed by default, and is read-only when expanded. A plan that is completed, cancelled or no longer advancing and has no active members can be closed from the card's top right; this browser remembers the hidden state for the current version without deleting records or modifying scheduling. The latest round can be expanded again from the "view this round's plan" icon, and a new plan or a status update shows it again. Only the `wb` CLI of a fixed supervisor Run shows the schedule capability and can submit, with the Home still validating the supervisor identity of the project; after submission the existing state machine advances automatically with no approval draft.
- `public/project-settings.js` and `public/project-space.js` provide one project settings page covering description, folder, all repositories and the supervisor configuration. `public/scheduled-jobs.js` is a separate full-screen page that summarizes jobs across projects and edits them in a single dialog through the existing project schedule API. `public/platform-admin.js` manages device onboarding, hosting accounts and the configuration assistant in the base settings, which also keep platform prompts and connection security. The device page merges connected Workers and server registrations into device cards. Gitee and GitHub are separate cards, and editing an account opens a dialog with token input. The supervisor prompt and the default CLI, model and reasoning effort for new projects share one summary card and one edit dialog. Token statistics and scheduled jobs each have their own entry at the bottom left. The normal workspace uses left and right 90vw drawers at widths up to 1000 px, and the desktop keeps three columns; gestures exclude editable controls, code and tables, horizontal scroll areas and text selection, and Esc, focus cycling and the reduced-motion preference are supported.
- `src/token-usage.mjs` handles old and new `ccusage` JSON, daily snapshots, the backfill cursor after a disconnect, and range summaries. The Worker runs the `ccusage` installed with the app and never downloads one on the fly. The Home collects when a Worker becomes ready, every 6 hours and on manual refresh, and overwrites the day's record by `nodeId + date`. An offline device keeps its history and resumes from `lastCollectedDate` (inclusive) when it comes back. Devices share `TOKEN_USAGE_TIMEZONE` (default: the system time zone), passed explicitly to `ccusage` so that Home and Worker in different time zones do not misplace the day boundary. `public/token-usage.js` draws device-composition pie charts and a daily bar chart in native CSS, with no charting framework.
- The role configuration form shows the role name, template and machine, then the agent, model and reasoning effort, which is shown according to the model's capabilities. After a successful save the dialog closes and the list refreshes; a validation failure keeps the input and the error.
- The chat input does not truncate in the browser. Pasted or typed content over 8000 characters or 80 lines is converted automatically into a Markdown attachment using the existing project attachment and cross-device verification chain. Markdown and TXT attachments offer formatted or plain-text full previews, and copy and download keep the original. The limits of 6 attachments per message and 20 MB per file apply; exceeding them shows an explicit hint and keeps the text.

## Project directories and repository configuration

`GET /api/workers/:id/directories` sends the directory query to a Worker that declares the `projectBrowser` capability. It returns only real folders inside the allowed roots, excluding hidden directories and symbolic links, at most 200 items per page. The Home does not read the user's machine. The selection result is the canonical path on the node and not a browser upload path.

Creating a project requires `folderName` and `supervisor={nodeId,runtime,model,effort}`. The Home validates online status, authentication, model and the `projectSpace` capability, and the Worker then prepares "device default workspace / project folder name". The supervisor can be on any device, and the project and supervisor are stored together. Existing files of the same name are not overwritten, and old directories and historical Runs stay unchanged. Roles read and write all repositories of the project uniformly; on one device work is serial by default, only supervisor-approved isolated batches can run in parallel, and across devices each Worker executes.

A Project has `repoUrl` and `repository` (owner/repo/webUrl). `POST /api/projects/:id` updates the name, description and links and rejects embedded credentials and other protocols. `POST /api/projects/:id/git-check` checks read capability with a non-interactive `git ls-remote` on a specified bound node; credentials stay on the node, and saving or checking changes neither origin nor clone/push. The check result is stored per project and node and bound to the URL and `localRoot`, so an old check is not displayed as current after the configuration changes.

## Conversation and roles

Browser state refresh remains single-flight. Each state GET has a 20-second deadline covering headers and body; timeout aborts the request and releases the refresh lock. Late responses cannot replace a recovered snapshot. Read failures invalidate the delta cursor so the next poll loads a full snapshot, preserving the displayed state and unsent drafts meanwhile. Focus, visible-page activation, page restoration and network recovery also request a refresh. Connection details show the last successful application of state, not merely an open event stream. Message submission and other writes are not automatically retried by this mechanism.

### Same-device CLI handoff

`RoleSwitches` persists one switch operation per role. `RoleSwitchRuntime` drains accepted work, records a source handoff, starts a separate staged native session and validates its acknowledgement. `RoleSwitchWorker` holds a durable role barrier, retires warm processes, checks native completion and compares Git/file metadata. Home atomically promotes the candidate and updates all fixed-supervisor records; queued execution waits for the Worker release receipt. Historical request snapshots remain unchanged, with a separate `executionBinding` for undispatched work (including dependency stages).

Both role editors use `public/role-switch.js`, with a renewable lease and authoritative cancellation/commit status. Full platform history is a hashed, role-specific artifact transferred through authenticated HTTP rather than a large WebSocket command. Candidate sessions are labelled staged, and maintenance is excluded from business reports and role calls. Codex maintenance uses a read-only sandbox; Grok maintenance exposes only `read_file`, denies prompting for additional tools and disables subagents/web tools. Business-run permissions are unchanged. Claude/Antigravity switching and older Workers are explicitly unsupported until validated. See [the handoff design](design-role-cli-switch.md) for cancellation and acceptance boundaries.

Role display names are stored user data and are never translated during routing. Unmentioned intake uses `project.supervisorRoleId`, and an explicit `targetRoleId` stays a direct dispatch even if an existing role has a name that collides with a broadcast keyword. New names cannot claim `all` or `everyone`. Shipped template names follow the same no-spaces validation as custom roles. Browser autocomplete and server mention parsing both recognize ASCII and full-width punctuation; this preserves message routing but is not a UI language-switching feature.

Fixed role, tool and supervisor rules are separated from the per-turn `executionRules`, and the latter and the new tool entry are sent in full each turn. The Home passes `task.runtimeInstructions` separately only to a Worker that declares `stableInstructions=1`; an old Worker still gets the full original format. The Worker's warm-process fingerprint includes the role name and the fixed rules, so changes of the temporary Run, the bridge and the report requirements no longer interrupt a warm process. Antigravity uses `event:user` streaming input and keeps the process alive after `result` (it needs a version that supports `--input-format stream-json`); Grok still cold-resumes. `instructionDelivery` lets Antigravity inherit the rules only from a successful earlier turn of the same project, node, role session and native ID; Claude records rule inheritance only when a warm process was truly reused, and the system configuration of Codex and Grok is always supplied in full. `sessionReuse`, `instructionFingerprint` and `instructionsInheritedFrom` are stored with the Run state.

`buildRunContext` stores the full snapshot and `inheritedContext`. `renderRunPrompt` only omits identical background fields or messages from a successful earlier turn of the original session, and never the current original instruction, explicit quote, delivery or execution boundary. Without evidence of successful delivery nothing is trimmed. Group-chat analysis remains an ordinary reply; the question of `wb call` and the receiver's result are separate linked records, and an `@` in model text does not dispatch.

The role form shows no permission, project directory or primary repository option, and internally uses `workspace-write` uniformly. It only selects the device, the actual CLI and model of that device, the reasoning effort and the prompt. When a directory is missing, the user goes to the single project-settings entry to prepare it. All repositories are fixed per Run. The old primary-repository association of roles is dropped in the startup migration, and historical Runs are not rewritten.

`src/runtime-probe.mjs` probes local CLIs: Codex uses a short-lived App Server to read authentication, the model catalog and rate limits; Grok and Antigravity read `--version` and `models`; Claude Code reads `--version` and `auth status`. Quota probes are best-effort per CLI. Codex account reads and Grok ACP billing do not create a Thread/session; Agy uses built-in `/usage` and `/credits`. Both Claude `/usage` paths receive a copied subprocess environment with `CLAUDE_CODE_SKIP_PROMPT_HISTORY=1`, suppressing prompt/transcript persistence on compatible versions without changing normal conversation environments. No probe submits a model turn. The Worker declares the `runtimeDiscovery` capability, probes at startup and every 5 minutes, and a manual `runtimes` query can refresh it; concurrent probes from one Worker are merged. A report contains only the version, whether authentication is ready, support flags, models and reasoning levels, quota where available, and the detection time. OpenCode is only detected by version, and anything without an adapter is not marked executable. Gemini is no longer probed, and the Home state snapshot also filters Gemini reports from old Worker caches.

The shared role quota renderer displays body-level hover/focus hints outside the clipped percentage glyphs; click/touch/keyboard activation opens a quota dialog instead of the role editor. It uses only that role's existing runtime/model quota and preserves the vendor's reset text and timezone rather than guessing from incomplete Claude date strings. Missing reset times are explicit. Hints are removed when their card detaches or the viewport scrolls/resizes; closing the dialog removes it. This UI does not refresh quotas, dispatch work or mutate role/session data.

`POST /api/workers/:id/runtimes` runs a probe on the chosen device, and `runtime_report` updates the Home mirror. Before saving a role the Home checks online status, a live probe, the actual directory and a matching model. Rooms and the Worker validate the model and CLI with the same `runtimeIssue` rules, and a probe older than 10 minutes waits for an update. Disabling an existing role can be done offline and keeps its configuration. Model selection does not use a global fixed list, models of different machines are not interchangeable, and a missing old model is not replaced silently.

The refresh on the role bar merges the above detection per device and shows "detecting" and the result. A temporary network error, a query timeout or a 5xx is retried at most once, while an explicit authentication failure and 429 are not retried automatically. Only status queries are retried, and business tasks are never dispatched or resumed. An idle role card prefers a detection report newer than the last run failure; an older report cannot override a newer failure, and an expired report is not marked available. Executing, queued, awaiting reconciliation, approval, discussion waiting, launch blockage without a Run, and business verdicts that need handling keep their original priority. A failed manual detection is shown separately; the error, status and report of the original Run are fully kept. "Available" only means the no-reasoning probe passed and is not equal to a successful vendor model call.

Each project has one Room, and users do not fill in task forms. The underlying Task/Run records responsibility and run state, and `coordinationRequests` records cross-role calls. In a project with a configured supervisor, no `@` routes to that supervisor by ID; an explicit mention uses the exact stored role name (`@Supervisor` in a new English project). Without a configured supervisor, unmentioned text is discussion only. In all projects `@all` remains an announcement. An explicit `@` takes up to 4 worker roles: a single one dispatches directly, and several only create a supervisor evaluation turn with the named roster fixed. Ordinary agent output does not trigger dispatch. The built-in `wb` provides memory/docs, Git status, notes, call/wait/deliver, the supervisor's schedule, setup catalog/propose and role prompt. Repositories, new roles and device configuration are confirmed through cards, while the prompt of an existing worker role can be updated directly by the fixed supervisor. After a configuration card is confirmed only clone or binding an existing directory is supported, and there is no arbitrary pull/push/sync. The hand-off of an isolated execution is written to this Run's `.workbench`, and for an ordinary shared execution `LATEST.md` stays the index of the latest hand-off on that machine.

The project and the fixed supervisor configuration, the internal `systemSupervisor` role and the welcome message are stored together. The ordinary roles interface filters this internal role, and the supervisor is configured only in project settings. Worker roles are not created automatically and templates are only shortcuts for filling in. The platform configuration assistant uses a hidden system project and a fixed prompt, and after a web-confirmed proposal calls the same device and project operations; account secrets do not enter directory queries or prompts. The current implementation provides lightweight stage scheduling and does not include general plan revision, automatic repair loops or automatic cross-device pushes.

Roles store a revision. An edit can carry the old revision to prevent overwriting, and requests and Tasks fix a `roleSnapshot`. Archiving keeps the role and history and is rejected while the role has unfinished tasks, Runs or calls.

`role-calls.mjs` manages persistent `coordinationRequests`. Notification, consultation and delegation remain distinct. A continuation is a new Run of the same owner/device with its existing call chain, workspace and native association; prior process/tool settlement and authorization gates still apply. Explicit waits persist original dependency IDs and a deadline (default 30 minutes, override 60 seconds–24 hours). Expiry records one event and can resume the parent without cancelling or replaying peers. The parent can wait on the same request again; late answers follow its current continuation. Transactions and stable continuation IDs prevent duplicate wakeups across deadline/reply/cancel races and Home restart. Pending unselected dependencies remain waitable after a selected subset completes. Paused/cancelled/steered tasks are not revived. The four-level/20-work-request limits exclude timeout continuation bookkeeping.

`wb report` in a discussion or asked Run returns `ignored` and writes no business report, and a Run that already has a report is rejected before the side effects of the ask transaction. The Home stop entry always calls `RoleCalls.stopRun`, saving the command, the exact `stopRunIds` and the state in one transaction. Retransmitting an old command does not rescan Tasks, and call cancellation still re-sends the original stop targets with `cancelRunIds` without unlocking early. Stopping a clarification only aborts the handling of the current question; the original Task is blocked and the question is kept, and the user can reply or resolve manually or stop the original task from the question card. If the consuming turn fails after resolve, the intent and the Task are blocked; after a safe cleanup, a web confirmation record bound to thread/`afterRunId` is required to continue the original Task once. The stop entry stays available while queued, and an immediate steering invalidates a blocked intent. Claude's native `thinking_delta` only produces a generic activity log at most once every 15 seconds, stores no thinking content and estimates no progress.

`git-delivery.mjs` provides workspaces at a fixed SHA, pushing and receive-side verification. After a delivery is registered it waits for both the source success and the web push confirmation, and pushes to `refs/heads/agent-delivery/<id>`; once ready, cross-node references are allowed. The publish result and the Worker outbox are saved atomically, and a crash during publishing marks it pending reconciliation without blindly re-pushing. The first batch requires the role to produce a Git commit first; automatic commits from a file list and automatic authorization by plan are not implemented. The protocol requires the Worker `coordinationVersion=1`.

A role stores the node, runtime, model, permission and Markdown instructions. The available choices are Codex, Grok Build, Antigravity and Claude Code that the node probed as supported and available. Every assignment fixes the role snapshot and injects the role instructions into this execution without overwriting the project's `AGENTS.md`. Changing a role affects only new messages; disabling a role pauses its queue, and operations already running need to be stopped separately.

Role templates provide a short responsibility for collaborator selection and an empty execution prompt; the editable supervisor prompt also defaults to empty. Clearing saved execution prompts is an explicit operator action, not an automatic migration of custom role text. Existing histories and frozen run configurations remain unchanged, while later turns use the cleared components and the existing revocation-event mechanism.

The message `clientMessageId` is bound to its parameters, and the message and the internal dispatch to the recipient roles are committed in one synchronous SQLite transaction. Offline messages queue; the Home allocates by one active Run per role and node capacity, and starts only after the Worker finishes reconnect reconciliation and the runtime is available. Pause rejects new `@` messages and keeps the existing queue, and ordinary chat is unaffected. An unstarted assignment can be cancelled; a process awaiting reconciliation blocks further dispatch on the same node.

A completion message is stored uniquely as `result-runId`, linked to the Run's terminal state and the source message. Retransmitted events and Home restarts do not post to the chat twice. Token and tool output goes only into the details, and the group chat loads the most recent page after an increment via the Room revision, without re-reading history on every token. Messages are 60 per page, and drafts and unconfirmed sends are stored per project in the browser session.

Quoted context is limited to 8000 characters and the whole group history is not injected. A same-node quote writes the source workspace path into the context. A cross-node quote requires exactly one `ready` Git delivery, the task carries a `deliveryId`, and the receiving Worker does not need the local database record of the source Run; with no delivery or several ambiguous deliveries it refuses and explains.

## Execution and state

Report submission has a durable receipt bound to Run, submission ID and normalized content. The report, Run projection and receipt commit atomically. Same-ID replay returns its original revision without overwriting a later verdict; identical content derives the same ID, while an explicit new ID allows a deliberate revision. After a transport timeout the shared `wb` client queries the receipt, retries at most once only when a compatible Home confirms it is absent, and reuses the same ID. Unavailable confirmation returns `pending_confirmation`, never an invented failure verdict. `wb report status ID` reads receipts, including settled Runs when their bridge remains available; it does not reopen execution or permit new terminal-state reports. Legacy saved reports can be recognized by matching content without rewriting their revision. Older Homes that lack confirmation support are not automatically retried.

The terminal event's event/Run update, the RoleCalls wrap-up and the Room result message are committed in the same Home SQLite transaction, and the ACK is sent only after the commit. On startup the terminal wrap-up is replayed to repair old crash windows, and existing terminal business verdicts are not recomputed. A cancel request or a cancelled plan is not continued automatically. When startup validation rejects, the Task and the corresponding unstarted Call are closed together, so no queued call without an execution can block a plan or scheduled job.

A Codex pipe error only fails the current session or marks it pending reconciliation and does not bubble up to terminate the whole Worker; a closed RPC connection is rejected immediately. A managed process that ended normally or failed to start gets SIGTERM first and SIGKILL if still alive after 3 seconds; this must not be used to mark active tool results as successful. Front-end file preview and the desktop link isolate stale responses by request generation, and paged history text shares an in-flight request serially per view state so that copying does not repeat segments.

A Project stores the collaboration identity and a stable `folderName`; `repositories` identify a repository by `projectId + key`, and `repositoryWorkspaces` bind a directory by `repositoryId + nodeId`. A Run fixes `projectRoot` and the full set of repositories, a missing working repository blocks the start, and the supervisor can still help complete the configuration. `project-delivery.mjs` publishes and receives per repository SHA, and the receiver generates a set of fixed-commit directories in the project. Uncommitted files are not synchronized, the original branch is not switched, and atomic multi-repository commits are not promised.

`setupProposals` are proposed only by the current project supervisor's Run. A fixed entry outside the chat scroll area shows the selected project's pending count and opens its configuration cards in a dialog; reading or closing that dialog does not approve anything. After web confirmation the repository and role actions run in order and each result is recorded; confirming again returns the existing state. The Worker's `setupOperations` records results by operation ID, and a failure, restart or timeout requires verification and is not overwritten or redone automatically. Successful configuration results enter the group chat and are read by the supervisor on the next turn. The model is a trusted-operator one, and the tool allow-list is not complete isolation against a malicious shell on the same account.

`wb role prompt` goes through a separate agent bridge allow-list and Worker credential and accepts only an active Run of the fixed supervisor of the current project. The Home verifies the role ID, the current revision and a stable request ID, and within a transaction updates only `instructions` and the revision of a non-system worker role. A retry with the same ID returns the original result, and a conflicting ID or stale revision is rejected. `rolePromptChanges` keeps the text before and after, the source Run and the time, and the project group chat receives a version summary. Generated Tasks and Runs keep the original role snapshot, and only later new messages use the new version. Deleting a project cleans up the audit records too.

A new dispatch must have a node binding. When creating a Run, `localRoot` is fixed as `projectRoot`. Delivery and command retransmission use that snapshot, and configuration changes do not affect existing Runs. The Worker checks the path again before starting. An old Run without a snapshot keeps the original project path, and a new dispatch of an old project must first add a binding. The Worker declares support for path queries through `capabilities.workspaceBindings`.

Worker registration also reports `nodeKind: local | cloud` and optionally the legacy `remoteDesktopUrl`. An explicit `NODE_KIND` wins; by default Linux is recognized as cloud and other platforms as local. The Home only stores and mirrors this fact, and the UI uses it to choose local or cloud-server icons and text instead of guessing from the device name. A legacy link may only be `rdp://` or `http(s)://`, and script protocols, overlong values and password or token parameters are rejected. On a macOS Home, the bottom-left and the device card share a remote-desktop entry: it first probes the remote loopback xrdp port with the SSH key of a registered device, then establishes a separate local `-L` tunnel and finally starts the Windows App client; the user then clicks the connection saved in the client and reuses its login credentials. The page gives feedback per stage but never reports "client started" as "desktop logged in". No new `.rdp` connection is generated, the Worker's reverse tunnel is not modified, and the client login screen is not operated automatically. A Linux Home hides this macOS-specific shortcut.

If the configured local desktop port is already listening, macOS process inspection can reuse a same-user SSH forward only when its explicit loopback mapping, registered SSH destination and established connection match. Conflicting same-port declarations are rejected. The external process is revalidated before client launch; its record is discarded on configuration change or Home exit without terminating it, so any other forwards it carries remain intact. Unknown listeners and failed inspection stay blocked. This is a trusted-operator compatibility check, not an isolation boundary against malicious processes on the same account.

Creating a task only stores the requirement. When execution starts, a transaction checks the `commandId` and whether the current Task already has an unfinished Run, creates a stable Run and then dispatches. The Worker writes the command and the Run to its local database before starting the process. Network retransmission reuses the command ID. File and path queries are bound to the target node and fail immediately when disconnected.

Worker events have their own ID and a per-Run `seq` and are stored locally as pending first. The Home persists and de-duplicates before acknowledging. An old sequence number does not overwrite new state, and events of an old Run do not modify the Task of a new Run.

A stop request records `stopping`, and only an `interrupted` from a real `turn/completed` is a normal stop confirmation. When the App Server exits abnormally while a turn is active, the state is kept pending reconciliation so a tool is not wrongly assumed stopped. A Worker restart only reconciles the recorded processes and does not restore external sessions.

The legacy manual confirmation only applies to the latest successful Run. The group chat shows execution completion and the role's verdict and does not claim business acceptance automatically. A user can currently quote a delivery to let an independent role review it, but a fixed-commit Review entity, automatic review forwarding and automatic Git merging are not implemented.

## Optional WeChat numbered channel

`src/wechat-channel.mjs` runs only on the Home and calls the HTTP API of an external confirmation hub directly. It is off by default, and its configuration and bearer token stay in a private directory on the Home (`WECHAT_CLIENT_CONFIG` or a per-client file; the client name comes from `WECHAT_CLIENT`). The `wechatSettings` record in SQLite stores the switch and health, `wechatLinks` stores the message UUID, the original Run/project/role, the hub UUID, the consumed `seq` and errors, and `wechatResolvedQuestions` stores question versions already handled on the web. The UUID is stored before sending; a creation timeout reuses the UUID, and reply dispatch and `seq` are stored in one transaction. A background check runs every 4 seconds, with back-off on network errors and no retry on authentication errors. The public status fields contain no credentials or original approval fingerprints.

A role asks a question with the existing `wb report needs_input`, the CLI can exit normally, and the Home keeps the wait without occupying a Worker slot; ordinary questions have no local wait limit. A WeChat reply goes through `Rooms.post` into the existing queue and native session resume and runs no free-form shell. A message quoting the question on the web and the handled mark commit in one transaction, so no WeChat notification is added later even if it was not yet created. Questions are distinguished by the original Run plus the report revision. The settings dialog can turn off follow-up manually. New instructions bind the project only by number, and `@role` reuses the existing group-chat dispatch rules.

The shared `wb help` output documents an executable `needs_input` example, replying to the original role on the project page, optional WeChat delivery, and the distinction between user questions, peer waits and operation approvals. Discussion-only turns return unresolved user questions to their original business task instead of writing business reports. These operational details are available on demand; the editable platform prompt need not duplicate the command manual.

Native approvals and the web reuse the `respondApproval` validation, and only hub `approved/rejected` can be submitted. Expired, already handled, parameter-changed or stopped runs no longer authorize, and long or sensitive approvals only notify the user to review on the web. The first ordinary reply is always consumed first (including catching up when offline); the extra instruction window of an already answered number is 23 hours, earlier than the hub's retention of at least 24 hours for numbers, and is not a permanent project address. Configuration cards, Git delivery and cross-project messages without a number are outside this channel.

## Native permissions

Codex uses `thread/start`, `turn/start` and `turn/interrupt` of the App Server. The sandbox is uniformly `workspace-write` and `approvalPolicy` is uniformly `never`; the workspace is created and restricted by the Worker beforehand. Both new and resumed sessions explicitly enable the network to support Git and cross-device communication. The extra writable scope only adds the current directory and the git-dir and git-common-dir that Git resolves for bound repositories, so that fetch and commit in a worktree are not blocked by read-only metadata, and the whole user directory is not opened. Git hosting authentication still has to be configured separately, and network access does not mean repository access exists.

The protocol reference is the Codex App Server documentation. The sandbox enumeration in an online documentation example once differed from the installed version and was corrected to the real interface response, so it must be verified again whenever the runtime is upgraded.

Codex, Grok, Antigravity and Claude Code all auto-approve tool calls inside the project workspace assigned by the Worker. Claude Code uses `--dangerously-skip-permissions`, Grok uses `--always-approve --permission-mode bypassPermissions --no-plan`, and Antigravity uses `--dangerously-skip-permissions --mode accept-edits`. The page does not wait for per-step approval for these runtimes; interactions of unknown runtimes are still rejected and recorded.

Each execution inherits the node's native CLI login and user configuration, and global Skill/MCP instructions are not isolated separately. The related context counts toward runtime usage; the UI shows total input and cached input and does not treat cumulative input as uncached billing.

## Current limitations

### Opt-in collaboration session queue

`collaboration-sessions.mjs` owns membership and review visibility; `session-queue.mjs` keeps receipts, collectors, batches and cycles in the existing Home store. Explicit requests reuse their formal Task without a second driver. Runnable collectors rotate without allowing paused or protected work to starve others. Project settings save collection times, backlog thresholds and future-cycle budget atomically. The feature defaults off; the twenty-batch seed applies only to test projects, not business projects.

Home reserves capacity and budget. Worker protocol 2 rechecks the actual native-input boundary, and native acceptance charges once. Verified non-delivery refunds; unknown delivery stays linked to the original Worker/Run for verification, without redispatch. Known startup failures block repeated attempts until relevant facts change. Old Workers cannot consume new batches or protected-review inputs.

New automatic consultations and clarifications inherit the same cycle. Answers and necessary resumption of accepted work do not charge again. The original batch survives call/wait and discussion/reply/resolve through `continuationBatchId` and its effective Run binding. Native output remains private; pass and explicit publication are validated separately, and a generic note cannot satisfy pending addressed requests.

The review-bound store filters before paging, summaries and input assembly, traversing request/Run/Task provenance and child topics. Removed reviewers remain protected until release. Managed documents compare server-captured hashes to actual Worker files and use role-private handoffs with canonical paths. This does not sandbox arbitrary native shell reads, detect unlinked paraphrases or erase previously seen content. See [V3 acceptance](design/session-queue-v3-acceptance.md) for measured scope and remaining drill limits.

### General limitations

- The current state is a development-grade managed execution. Multi-user permissions, per-device revocation, Project Epoch and manual primary/standby switching are not implemented. The default listener stays on loopback.
- Not implemented: automatic AI supervisor decomposition and forwarding beyond the lightweight stage scheduling, multi-user identities, other ACP runtimes, Feishu. Automatic recovery of native sessions has not been verified for every CLI on two devices; Grok, Antigravity and Claude Code have no native per-step approval comparable to Codex.
- Data is persisted on a single Home with no cross-host replication.
- File preview allows only ordinary text files inside the currently registered workspace, with limits on size and traversal depth; it is not a full project file manager.
- An unknown run of the same task cannot be retried automatically; the original process needs manual verification.
- SSH onboarding requires Node.js 22.16+, npm and Git on the remote machine. The background Worker is supervised but no boot service is installed. Installing a CLI does not do the native login for the user.
- GitHub/Gitee account and repository-creation interfaces are covered by simulated-response tests; authenticated creation needs a user token to verify. Creating a repository after an external API timeout needs verification and is not repeated automatically.
- Token statistics cover the CLI history that a device's local `ccusage` can recognize. They are not a vendor bill or the remaining account quota, and a device without local history shows 0. A single range covers at most 366 days.

These limitations stay visible, and simulated events, fake online status or static cards are never used in place of real capabilities.
