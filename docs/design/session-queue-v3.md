# Workbench 会话协作与 CLI 外部队列设计

**版本：最终设计 V3**  
**用途：开发与验收依据。设计定稿不代表新增机制已实现或部署。**

本稿统一此前讨论及评审意见，替代本会话中的旧版群聊协作方案。已有能力先核验、再复用，不重建第二套调度或工具系统。

## 一、目标与实施边界

让项目成员围绕目标直接讨论、询问和反馈，主管负责新会话初始化及必要协调，不逐条审批成员发言。

核心流程：

> **总管建立会话 → 平台向参与者登记消息 → 消息在 CLI 外部等待和合并 → 确认可立即执行后投递 → 角色回复、等待或明确不发言。**

本次包括：

- 会话归属、参与关系和消息广播。
- CLI 外部持久化队列、批次合并及公平调度。
- Worker 启动预留、租约及状态核对。
- 统一不发言出口 `wb pass`。
- 自动传播周期、广播预算及暂停恢复。
- 积压提醒、主管静默跟进衔接。
- 平台级独立审核信息隔离。
- 四家 CLI 的兼容验证。

不增加小模型，不清空已有历史，不自动重建原生会话，不扩大任务授权。IM 通知保留扩展位置，本次不实施发送。

## 二、概念与职责

### 2.1 核心概念

| 概念 | 含义 |
|---|---|
| 协作会话 | 围绕一个目标展开的议题 |
| 原生会话 | Codex、Claude、Grok、Agy 自身保存的对话 |
| 回合／Run | 一次实际执行 |
| 消息批次 | 本次交给某角色处理的一组确定消息 |
| 传播周期 | 一次讨论的自动传播预算归属 |
| 明确请求 | 已登记接收角色及请求编号、需要回应的事项 |

同一个项目群聊可以交错包含多个协作会话。一个角色可以参与多个会话，但同一原生会话不能同时执行两个回合。

### 2.2 职责划分

- **总管**：初始化新会话，处理分歧、阻塞及需要协调的提醒。
- **Home**：保存消息和队列，管理参与关系、预算、派发与处理进度。
- **Worker**：核对执行状态，预留位置，启动或续接 CLI，回报结果。
- **CLI**：处理实际收到的输入，自主决定执行、回复、协作或不发言。
- **页面**：展示真实的消息接收、排队、执行和处理状态。

**队列的权威存储位于 Home，CLI 不承担排队职责。**

## 三、会话建立与议题变化

### 3.1 新会话初始化

总管根据用户目标登记：

1. 会话目标及预期交付。
2. 原始用户要求、必要背景与资料。
3. 参与角色。
4. 必要的初始任务分工。
5. 开放讨论或独立审核类型。

总管忙碌时，初始化请求也在平台外部等待，不能提前写入其 CLI。

### 3.2 已有会话直接广播

会话建立后，平台根据参与名单登记接收关系，不再调用总管逐条选择收件人。

总管在参与名单中时，作为普通成员接收；不在名单中时，通过必要协调事件或静默跟进介入。

加入或退出成员需要明确登记。成员变化不会自动增加广播预算，也不能删除已有明确请求。

### 3.3 议题归属规则

程序优先继承确定关系：

- 回复继承原消息所属会话。
- 咨询答复继承原请求所属会话。
- 执行汇报继承原任务所属会话。
- 迟到回复仍进入原会话。

没有关联的新输入，由接收它的 Agent 在正常处理时判断。出现独立新目标时交总管初始化，不增加专门的分类调用。

不按关键词、说话人或时间间隔机械划分议题。新会话建立不会关闭旧会话；归属不明确且影响操作范围时，再询问用户。

结束讨论只停止自动讨论投递，**不自动取消已经受理的任务**。取消任务须走明确的取消操作。

## 四、广播与明确请求

### 4.1 接收范围

已有开放会话产生新的完整消息后，平台为全部参与角色登记待处理消息。

- 发送者不会被自己的消息再次唤醒。
- 流式片段、日志和系统心跳不作为独立讨论消息广播。
- 重复投递不重复登记。
- 暂停、离线或忙碌时，接收记录仍保留。

**“平台已登记接收”不等于“CLI 已读取”。**

### 4.2 请求识别

明确请求必须来自真实用户指派，或通过协作工具登记，并包含接收角色和请求编号。

正文提及角色名称、引用中的 `@角色`，不能直接变成新任务。

例如 `@Claude 请核对结论`：

- Claude 承担回应义务。
- 其他成员收到讨论信息，可以补充，也可以不发言。

### 4.3 混合批次

本批只要包含**交给当前角色且尚未处理的明确请求**，就不能直接以不发言结束。

角色须针对请求：

- 回复结果；
- 说明阻塞；
- 或登记有效的协作等待，保留续接关系。

背景信息不因此获得任务或授权含义。一条泛泛回复不能把多个请求全部算作完成。

“必须回应”决定处理义务，不代表可以绕过执行容量、租约或传播预算立即启动。

## 五、CLI 外部队列与消息合并

### 5.1 排队边界

CLI 忙碌时，Workbench 可以保存、合并和展示待处理消息，但不得：

- 向 CLI 标准输入写入下一批内容。
- 调用原生内部排队、追加输入或中途引导接口。
- 提前写入原生聊天历史。
- 一次提交多个未来回合。
- 为同一原生会话另起并发执行。

CLI 主动查询聊天历史属于自主工具调用，不属于平台中途推送。

### 5.2 队列组织

每个“会话＋角色”保留一个未派发收集入口。后续消息加入该入口，不为每条消息建立一次执行任务。

角色忙碌期间收到五条同会话消息，下一轮可以一次收到五条原文，而不是排出五个模型回合。

不同会话保持独立关联；内容超过单批容量时按序分批，不调用模型摘要，不静默截断。

### 5.3 合并参数

项目级配置：

- `合并等待时间`：默认 10 秒。
- `最长收集时间`：默认 30 秒。

从最近一条新消息开始等待，但不得超过首条待处理消息对应的最长收集时间。

明确请求不必额外等待完整的讨论合并窗口；如果角色忙碌，仍在外部等待，并可携带已经积压的同会话信息。

两项为非负整数，最长收集时间不得小于合并等待时间。两项均为零表示不额外延迟收集，仍须满足空闲和容量条件。

**非法组合由服务端拒绝保存，原配置保持不变；页面同步校验。** 不静默交换或修正数值。

### 5.4 公平调度

首版固定采用**同一角色按会话轮转**：

- 每次从一个可执行会话取一个有界批次。
- 下一次优先检查其他可执行会话。
- 暂不可执行的会话跳过，但不删除其消息。
- 轮转位置持久化，避免重启后总从第一个会话开始。

轮转只决定下一批选谁，不打断当前 CLI。单个回合长期不结束，通过积压提醒处理。

## 六、空闲确认、租约与派发

### 6.1 空闲判断

Worker 必须确认：

- 当前原生回合已经结束。
- 没有未结束的工具执行或原生审批等待。
- 会话由当前 Worker 合法持有。
- 没有人工接管或其他有效执行占用。

低 CPU、暂时没有输出、进程存在或不存在，都不能单独作为结论。

等待的是**当前回合结束**，不是进程退出或空闲保活时间到期。可以复用的进程直接续聊；已经退出时沿用原生会话恢复。

### 6.2 派发流程

```text
消息持久化并登记接收关系
        ↓
满足收集条件，等待角色及设备容量
        ↓
检查会话状态、处理义务和传播预算
        ↓
Worker 核对空闲并预留执行位置
        ↓
Home 封存批次、配置版本和关联 Run
        ↓
Worker 再次校验预留，向 CLI 投递一次
        ↓
执行结束，保存结果及消息处理收据
```

批次封存后，新消息进入下一批，不改变已确定的输入。

### 6.3 预留租约

预留包含编号、有效期和代次标识。Worker 实际写入 CLI 前再次验证，不接受过期预留或旧代次启动命令。

租约到期分三种情况处理：

| 情况 | 处理 |
|---|---|
| 确认尚未投递 | 回收预留，消息重新等待 |
| 可能已启动，但确认丢失 | 标记待核对，查询原 Run、原生回合及进程 |
| 已确认启动 | 进入正常执行管理，不用启动租约终止任务 |

**租约过期不能证明旧 CLI 已停止。** 状态不明时不能直接重跑、迁移设备或创建新会话。

预留租约与外部队列在同一阶段实现，不留到广播上线后补充。

## 七、传播周期与广播预算

### 7.1 周期边界

新会话初始化时创建 `cycleId`，绑定来源用户消息和预算授权。

以下行为不建立新周期：

- 同一目标下的普通补充。
- Agent 回复、咨询或新增 `@请求`。
- 消息合并、进程重启。
- 十分钟静默。
- 修改会话名称或派生子议题。

派生讨论保留原预算来源，不能通过拆会话绕过上限。

会话明确结束或取消时，传播周期结束。预算耗尽是暂停，不是结束。

用户确认继续时，对原周期记录新的预算授权，**保留已经消耗的数量和原请求关联，不清零历史**。独立新目标由总管建立新的会话和周期。

### 7.2 计数与原子预占

### 7.3 上限与恢复

达到上限后：

- 暂停新的自动传播派发。
- 保留消息、接收关系和外部队列。
- 不停止运行中的 CLI。
- 不取消已有请求、答复和必要续接。
- 不把暂停标成技术失败或审核失败。
- 给主管登记一次去重协调事件。

已有请求的必要续接，不意味着可以无限新增自动工作。自动讨论产生的追加请求仍保留原来源并接受预算检查。

用户明确发起的正式任务、独立审核及其正常执行链，不被误算成全项目累计的讨论次数。

主管可以整理结论或请求用户恢复，但不得无限自动续额。

### 7.4 初始预算

项目配置一个明确的正整数上限。20 批作为隔离验收起点，不作为未经实测就固定的生产默认。

验收覆盖不同参与人数，记录有效补充、重复发言及触顶后的未解决事项，再校准默认值。参与人数可以影响预算建议值，但**周期中增加成员不自动增额**。

## 八、公开回复与 `wb pass`

### 8.1 显式公开

本机制产生的讨论批次，包括混合批次，采用统一输出规则：

- 流式文字、中间说明、原生最终回复和结束兜底只进入执行详情。
- 只有显式调用平台回复入口，才生成群聊消息。
- 已公开内容不因原生最终回复再次发布。
- 审批、用户确认和技术异常继续通过明确的系统入口展示。

普通用户任务原有自动回帖方式不在本次顺带改造。

### 8.2 不发言出口

新增统一工具 `wb pass`，语义固定：

> 当前讨论批次已处理，无需公开发言。

服务端从可信运行环境绑定项目、角色、Run 和批次，不接受模型指定发送者身份。

调用须满足：

- 当前批次归属正确。
- 没有未处理的明确请求。
- 没有与不发言结果矛盾的公开回复。
- 重复调用按批次幂等处理。

成功后保存处理收据，不产生群消息，不唤醒其他角色。

`wb pass` 不表示任务完成、审核通过或 CLI 已空闲。必须等原生回合结束，才能投递下一批。

四家 CLI 完成兼容验证前，不把 `wb pass` 写入实际运行提示词。

## 九、独立审核隔离契约

### 9.1 首版保证范围

本次保证：

> 本轮独立审核期间，审核者不能通过 Workbench 读取入口获得其他审核者尚未释放的受保护意见。

由服务端依据项目、审核批次和可信身份校验，不能只靠不广播或提示词提醒。

过滤覆盖：

- 历史列表、全文和按编号读取。
- 搜索、引用展开。
- 报告和执行记录。
- 摘要、附件和文档入口。
- 从受保护意见派生的内容。

读取权限先于结果展示、摘要生成和分页处理。独立审核阶段不自动把其他意见转入审核者的新输入。

### 9.2 释放与边界

审核者提交自己的意见，不代表立即获得其他人的意见。按用户约定进入共同讨论后，才统一释放相关内容。

本轮受保护意见不自动写入公共群消息、共享文档或同步目录。

本次不承诺阻止任意终端文件读取，也不能消除原生历史中已经见过的内容。如果受保护意见已经进入共享文件或原生上下文，应记录隔离限制，不能宣称严格盲审。

严格盲审需要另行确认文件权限和原生上下文隔离；本次不自动清历史、重建会话或更改项目文件权限。

## 十、积压与主管跟进

### 10.1 积压提醒

页面显示待处理数量、最早等待时长、所属会话和等待原因。

数量或时长达到项目阈值时，向主管发送一次去重提醒。积压未改善时不反复发送；恢复后再次越界，才生成新事件。

主管可以调整讨论参与范围，或考虑改派明确任务。改派前核对原执行是否已经开始，保留请求关联，避免新旧负责人同时执行。

平台不自动丢消息、清队列或抢占当前 CLI。

### 10.2 静默跟进

准确计时规则：

> 从 Home 持久化最后一条新的有效完整聊天消息开始，连续十分钟没有新的有效消息，登记一次主管跟进。

不是“没有新会话”。消息即使仍在平台队列，也已计入。

正常用户和 Agent 完整消息计入；流式片段、日志、心跳、重复投递、`wb pass` 及主动跟进自身提醒不形成新周期。

同一静默期只登记一次。主管忙碌时外部排队，启动前复核最新消息；过时提醒撤销并重新计时。

广播超限、积压和静默提醒针对同一事项时合并处理。明确请求及已有协作答复不额外等待十分钟。

后续 IM 用于用户决定、补充信息及授权。本次不实施真实通知发送。

## 十一、工具、身份与提示词

先核验现有 `wb help`、团队查询、历史查询及身份绑定，补齐缺口，不重建同类入口。

Worker 提供当前 Run 的可信身份和工具环境，服务端校验项目、角色、任务及批次。模型不能通过参数冒充发送者。

提示词不变，也必须正确更新当前 Run、工具入口和权限环境。配置变化在下一轮实际启动时应用，已启动回合保持不变。

### 平台公共提示词

> 你是当前项目的协作成员，任务可能来自用户、主管或同伴。按任务需要自主执行或协作。需要了解前情、寻找成员、联系同伴或请求用户确认时，可通过 wb help 查找入口。开放讨论中有实质补充再参与，无需发言时使用 wb pass；对明确交给你的问题或任务，回应结果或登记等待、阻塞。

### 主管专有提示词

> 协助用户推进目标，协调成员并处理遗漏、分歧和阻塞。新会话明确目标、背景、参与者及必要分工；已有会话让成员直接交流，尊重已有任务安排和独立审核要求。收到跟进或异常提醒时结合最新情况判断，有必要再介入，避免重复派工。需要用户决定或新增授权时，说明具体问题和选项。

具体操作、参数和错误处理放在工具说明及 `wb help`。不替换 CLI 原生指令，不擅改用户自定义提示词，不规定固定专业流程。

## 十二、持久化与界面语义

复用现有消息、请求、Run 和原生会话记录，补充：

| 记录 | 必要信息 |
|---|---|
| 会话 | 目标、参与者、类型、关联任务、开放状态 |
| 接收关系 | 消息引用、角色、明确请求、处理收据 |
| 批次 | 消息范围、配置版本、Run、结果 |
| 传播周期 | 来源、授权预算、已用和预占数量、暂停原因 |
| 预留 | Worker、位置、有效期、代次、启动确认 |

处理确认以消息明细为依据，不能推进一个最大序号后跳过未处理内容。

回复保存或合法 `wb pass` 后，确认对应输入已处理；原请求仍可能处于协作等待，不自动标记业务完成。

页面区分：

- 平台收集／排队。
- 待核对执行状态。
- CLI 正在处理。
- 本批已处理。
- 自动广播暂停。

技术执行状态与审核通过、不通过等业务结论分开。

重启和断线后先恢复、核对记录，再决定是否重试。取消任务和撤销权限不经过普通消息合并窗口。

## 十三、实施顺序

1. **工具与权限基础**  
   核验现有入口、身份绑定、团队和历史查询，补齐审核记录过滤及会话关联。

2. **外部队列、批次、轮转和租约**  
   一起建立安全派发基础，验证忙碌期间没有任何输入提前进入 CLI。

3. **显式公开与 `wb pass`**  
   四家 CLI 分别验证流式、最终回复、工具回复和不发言路径；通过后更新提示词。

4. **传播周期与广播预算**  
   实现原子预占、来源继承、暂停及授权恢复。保护机制通过前不开启自动广播。

5. **积压、静默衔接及完整验收**  
   校准参数，验证提醒合并、配置校验和恢复路径。

内部可分阶段开发，但不得把保护机制未完成的中间版本直接用于真实项目自动广播。

新旧 Home／Worker 进行能力兼容检查。不兼容时保留外部队列并提示升级，不能退回“先把消息塞进 CLI”的方式。

## 十四、验收与发布标准

Codex、Claude Code、Grok、Agy 分别验收，本地与服务器分别记录版本和证据。

必须覆盖：

1. 新会话由总管初始化，已有会话广播不额外调用总管选人。
2. CLI 执行期间收到多条消息，原生输入及历史未提前写入；空闲后收到合并批次。
3. 同角色多个会话按轮转处理，不被高频议题长期独占。
4. 混合批次中，只有实际承担明确请求的角色必须回应。
5. 四家 CLI 的流式及最终回复均不会自动进入讨论群；显式发布只出现一次。
6. `wb pass` 幂等、无气泡，有未处理请求时被拒绝。
7. 并发派发不突破预算；Agent 新增 `@请求`、重启或派生话题不能重置预算。
8. 超限不取消已有请求，迟到答复和必要续接保持原关系。
9. 预留后 Worker 退出可以恢复；启动确认丢失时不会重复启动。
10. 历史、搜索、报告、引用和派生摘要均遵守独立审核权限。
11. 最长收集时间小于合并等待时保存失败、原值不变；相等时允许保存。
12. 断线、重投、重启和多议题交错不漏消息、不重复发布。
13. 积压提醒去重，改派前核对执行状态。
14. 静默按有效消息计时，同一静默期只触发一次。
15. 暂停、人工接管、设备容量不足和不兼容 Worker 均保持外部排队。
16. 本次没有未经授权的真实 IM 发送、会话清理或任务中断。

发布按项目启用，不默认打开全部真实项目。设计完成、代码完成、自动测试、真实 CLI 验收、本地部署和服务器部署分别报告。

**最终完成标准：消息由 Workbench 可靠保存、排队和投递，忙碌 CLI 不接收平台推送的新输入；角色在获得执行机会后自主协作，程序提供可核验的预算、隔离、租约和恢复保障。**
