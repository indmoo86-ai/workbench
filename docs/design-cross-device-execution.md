# 跨设备快速执行与 Mac 本机协同详细设计

版本：设计稿 v2.3

日期：2026-10-14  
状态：待评审，未实施；提示词为待配置正文，不代表已经写入平台或角色。

本方案让用户能够把服务器上刚保存的代码交给 Mac 执行，同时保留正式 Git 审核和交付流程。核心采用“基础 Git 版本＋不可变文件输入集＋目标设备准备回执”：自动同步负责提前搬运内容，任务快照负责固定本次运行输入，Git 负责正式开发历史和成果交付。

后台增量同步与前台任务独立运行。在已启用范围内，文件保存后仍会自动同步，空闲和安全窗口继续处理积压；“任务不等待同步”仅指不等待无关文件或整个项目完成。默认文件读取先核对源端本次内容，再复用同哈希本机字节；明确指定版本或允许缓存时按约定免查源端当前内容。

本稿在 v2.2 主稿上落实 v2.1 三家审核汇总及针对当前代码核验后的补充意见，是快速执行方案的唯一维护主稿；旧稿只作来源，不并行维护实施规则。审核汇总对应附件的 SHA256 为 `684f01c8180bc20b26c25ecae196db815fe318cd16422dd2c94c0ef482b474aa`，不代表三家已审阅本 v2.3。

三家对 v2.1 均为有条件通过，报告状态与正文条件分开；一家的原生 CLI 收尾失败仍保留，不能改成运行成功。此次仅修订设计，没有配置、代码、文件移动、发布或实测授权。原《远端开发与本机测试方案 v5》继续负责正式固定 SHA 流程，未被本稿替代。下一轮应针对同一 v2.3 文件哈希复核修改点，不能沿用旧稿 passed 当作新稿已通过。

## 1 目标与边界

### 1.1 用户得到的能力

用户可提出“把服务器刚保存的代码交给本机跑一下”，平台完成输入范围确认、冻结、缺失内容传输、本机隔离目录准备、实际执行和结果回传。用户不需要为了每次快速验证先提交 Git，也不需要手工复制文件。

正式合并、发布和验收仍使用固定 Git commit。快跑成功只能说明某份冻结输入在指定环境下通过了对应检查，不能自动替代正式审核。

### 1.2 本轮设计包含

- 查询、指定文件读取、保存代码快跑、固定 SHA 正式流程的分流。
- 快照身份、依赖范围、跨设备接收、隔离执行与结果契约。
- 超时、重复命令、取消、迟到回执和进程状态不明的处理。
- 存储复用、后台读取限制及可恢复的工作目录生命周期。
- “测试”“Mac 本机协同”角色职责与提示词，以及平台通用提示词调整。
- 实施分期、测试矩阵、真实 Mac/Linux 验收与安全发布边界。

### 1.3 本轮不包含

- 自动合并多个开发 Agent 的代码；开发成果仍交回 Git 分支与明确的合并流程。
- 自动推送、生产部署、数据库迁移或业务数据写入授权。
- 跨设备搬迁原生 CLI 会话、复制账号凭据或共享可写目录。
- 删除现有会话、审核报告、冲突版本、文件备份或运行历史。
- 用通用 bypassGitCheck 绕过正式版本门禁。

### 1.4 已有能力与新增能力

依据 v1 所描述的基线，现有 Home/Worker、范围绑定、单文件读取、内容哈希存储、同步日志、隔离 worktree 和 Git 交付可以复用。通用 Agent 跨设备文件入口、独立 file_set 输入准备及本文的新契约属于待开发能力。

F 通道的本机副本选择、按路径补齐与新鲜度回执也属于本稿拟议能力，不能把现有整范围同步直接宣称为已经实现按需单文件补齐。未支持这些能力时，可以明确使用已有的源端指定文件读取入口，不强制退回全项目同步。

实施前需核对当时源码、部署版本和 Worker capabilities。本稿对照代码基线 `5dafbdc`：回执对账、退避、到期队列与部分高频历史读取优化已经实现；该事实不表示 file_set、新鲜度补齐、资源配额或本文新租约已经实现。空闲 CPU 目标尚需按本文规定的同负载测试证明，不能把混合开发负载的测量直接当作空闲验收。

核验记录分别保存设计版本及文件哈希、Home/各 Worker 实际加载的 runtimeCodeCommit 与发布清单、源工作区真实 HEAD/dirty。审核材料中的项目绑定 `c0cc851` 不等于本稿对照的 `5dafbdc` 运行代码；文档提交也不代表运行服务已更新。部署与现场运行证据保存在私有验收记录中，不以设计文字替代实查。

### 1.5 修订后的首次验收范围

首次端到端验收限定为一个源设备、一个明确的源工作区、一个 Git 仓库和一个目标 Mac，贯通 S 冻结、准备、执行、回报及资源释放。已有 Q/F 入口先完成正确分流；F 的 source_current 必须实际核对指定路径，缺少按需副本能力时使用已有源端文件读取并如实显示来源。副本补齐作为单独可验收增量，不阻塞单仓 S 主线。

多仓库布局、declared_paths、非 Git 执行、文件系统原子快照与更强只读隔离在契约中说明边界，首次能力不支持时返回 unsupported，不以旧目录或缺失文件替代。后续逐项开放，每项增加对应设备验收。

原 v5 的基线配置、角色设备及审批选择仍由原项目决定。本稿不授权清空 baselineBranch/baselineRoot，也不默认选择 v5 的任何待决策实施选项。

## 2 四类任务与版本证据

| 通道 | 典型任务 | 必需证据 | 不必等待 |
| --- | --- | --- | --- |
| Q 查询 | 查设备、任务、日志摘要、获准的数据查询 | 设备、查询条件、采集时间；数据源确实提供时附快照标记 | 文件同步、Git clean、代码工作目录准备 |
| F 文件读取 | 优先读取已核验的本机副本，必要时只补齐指定文件 | 源端与实际读取设备、范围、路径、内容哈希、新鲜度及校验证据 | 全项目同步、无关文件或无关设备 |
| S 保存代码快跑 | 在 Mac 上运行服务器刚保存但未提交的代码 | 基础 Git SHA、inputSetId、最终文件清单摘要、本机准备回执 | 无关文件、无关设备、正式 Git 提交 |
| G 正式版本流程 | 正式代码审核、测试验收、合并交付 | 固定 Git SHA、审批、接收记录、实际执行版本 | 不得省略原流程的必要审核与审批 |

分类由用户目的决定，不只看命令名称。一次测试命令既可能属于 S，也可能属于 G；区别是本次结果是否用作正式验收依据。

如果读取任务后来需要执行代码，必须升级为 S 或 G，不能把一次 F 的文件哈希直接当作完整应用的输入证明。

### 2.1 后台仍然进行增量同步

只要项目已显式启用对应同步范围、设备在线且满足安全条件，文件保存后的变更就会在合并短时重复事件后进入后台同步。不需要等用户发任务，也不是只有完全空闲时才工作。

存在运行任务、终端接管、未知写入者或目录租约时，延后可能干扰它们的目标写入；无冲突的范围可以继续处理，安全、空闲后补上待同步内容。不要为了等待某个目录而暂停全部项目，也不要强制结束正在运行的 CLI。扫描和传输遵守并发、字节及资源限制，避免后台同步拖慢交互。

后台同步只写原本已授权的普通同步目录，不写 S/G 的任务执行目录，不扩大其他项目的启用范围。发生内容冲突时保留双方，不能用“同步最新”覆盖本机未提交修改。

### 2.2 文件读取按需等待

F 通道先核对请求者、源设备、实际源工作区、授权范围、路径和 freshness，再分支处理；不是先命中本机缓存再决定是否核对源端：

1. source_current 默认先在源端稳定读取指定路径，取得本次 observedAt、实际字节哈希和范围 generation；之后才可复用本机同哈希字节或只补齐缺失内容。旧回执、mtime 和“上次相等”不替代这一步。源端离线或持续变化时不能返回旧副本 matched=true。
2. expected_version 核对明确 expectHash、合法来源与本机实际字节，匹配即可读取，不要求另查源端当前 HEAD；allow_cached 只在请求已允许缓存时返回原 observedAt 与 stale 状态。缓存命中不增加读取权限。
3. 默认只读源端或受控内容缓存；可以复用符合本次模式的已核验普通目录副本，但不为了读取修改普通目录。Q/F 不创建执行 worktree，缺少按需补齐能力时使用已有源端指定文件读取入口，报告真实来源。
4. 本次读取只等待必要文件及共享资源的安全小块边界；不创建全范围采集，不等待无关批次完成。读取过程中绑定变化或字节不匹配时返回明确错误，不把其他版本当作成功替代。
5. 用户明确要求“落入本机普通同步目录并使用”时，另建可追踪的路径级落盘请求。它必须处于已启用 scope，指定目标路径/generation、来源与预期哈希，并经现有同步调度、冲突检查、apply journal、sourceSyncDevices 基线与上传/接收回执结算。来自开发 worktree 的内容还要有合法的源映射与获准导入规则；不能把它冒充普通源目录的观察基线。
6. 当前普通同步按项目批次串行；路径级落盘不能绕过正在处理的批次。显示 queued/waiting_batch、waiting_workspace 或 conflict 及原因，保留其他任务和本机修改。已在缓存可读不等于落盘完成；只有实际字节与同步基线/回执一致后才报告 materialized。未实现路径级 apply 时返回 unsupported，不直接写文件兜底。

只读内容补齐复用现有权限校验、blob 寻址、传输与确认机制，不更新普通目录同步基线。落盘是现有同步状态机的增量入口，不新增第二套基线、冲突系统或“只复制不记账”的同步器。后续后台扫描必须认出已结算内容，不能制造虚假冲突或把同一效果无限回传。

### 2.3 文件新鲜度与来源

拟议 `freshness` 有三种值：

| 模式 | 使用条件 | 本机副本要求 |
| --- | --- | --- |
| source_current | 默认；用户需要源端当前内容 | 本次从源端读取并确认哈希后，核对本机实际字节，或接收对应内容 |
| expected_version | 用户或任务指定明确 expectHash | 本机内容及范围来源匹配指定版本即可，无需把它升级成源端最新 |
| allow_cached | 用户明确接受已知缓存 | 返回实际哈希、原 observedAt 和缓存状态，不宣称最新 |

历史同步成功回执只证明其记录版本，不能单独证明现在仍是源端最新。`source_current` 的“当前”指源端本次稳定读取时刻，结果带 observedAt；不能保证读取完成后源端不会再次变化。多个文件的 F 读取分别记录哈希，不承诺整组的原子快照，需要执行或整体冻结时转入 S/G。

指定 expectHash 时按本次模式校验，不匹配就返回实际哈希和 hash_mismatch；不能自动换成别的版本后仍标记 matched=true。范围绑定变化会使旧来源证据失效，需要重新核对。

### 2.4 两个不可放宽的边界

数据库查询、实时进程和服务状态通过 Q 查询源设备或实际数据源，不能复制数据库文件来代替查询。读取源码或文档可以复用普通同步副本；执行代码仍须采用 S/G 固定输入与隔离目录，不能直接运行持续被后台同步改写的目录。

## 3 系统分工与角色分工

### 3.1 程序组件

| 组件 | 责任 |
| --- | --- |
| Home | 解析项目、权限和设备绑定；保存输入引用；协调准备及执行；记录回执与结果 |
| 源 Worker | 在指定范围读取稳定字节；生成输入清单；提供缺失内容；保留冻结证据 |
| 目标 Worker | 获取基础 Git 对象及缺失内容；建立隔离目录；校验实际文件；管理执行进程和产物 |
| 后台同步 | 在已启用范围内持续增量同步普通目录、预热内容缓存；冲突或可能干扰任务的写入延后，不改写执行快照 |
| 原生 Agent CLI | 在被分配的目录与权限内理解任务、执行获准工作、提交结果；不能自行伪造准备回执 |

复用现有 Home/Worker 通道，不新增第二个调度中心，也不要求设备之间开放额外互连端口。

### 3.2 两个 Mac 角色

| 角色 | 主要责任 | 不承担的责任 |
| --- | --- | --- |
| Mac 本机协同 | 检查 Mac 环境、接收任务交接、准备依赖、启动专属测试服务、核对地址和进程、收集本机证据、交还资源 | 不代替独立测试结论，不自动修改源代码，不接管其他人的 CLI |
| 测试 | 核对测试输入和环境，执行测试/真实页面操作，分析失败，形成可追溯的测试结论 | 不自动修业务代码，不以服务启动或编译成功代替业务验收 |

两者由角色 nodeId 绑定到指定 Mac Worker，不能仅凭角色名称或提示词改变实际执行设备。

如果测试角色已经能使用平台准备好的环境，可以直接执行，不强制“总管→Mac 本机协同→测试”多跑一轮模型。只有需要本机环境处理或现场交接时，才调用 Mac 本机协同。固定准备、查询和启动动作优先由确定性的 Worker action 完成。

## 4 版本身份与快照契约

### 4.1 四种身份不能混用

- Git commit SHA：正式仓库版本，标识提交树与提交关系。
- 文件 SHA256：某个文件实际字节的内容身份，不表示整个应用版本。
- inputSetId：本次冻结输入契约的内容摘要，标识基础版本和完整覆盖层。
- preparationId：一次目标设备工作目录准备记录。相同 inputSetId 可以在不同设备产生不同 preparationId。

“同步批次已完成”“消息已送达”“Worker 在线”和“这次输入已准备好”是不同事实。

### 4.2 输入集合结构

下列字段均为拟议契约，不能当作已发布 API。

```json
{
  "schemaVersion": 1,
  "digestVersion": 1,
  "kind": "file_set",
  "projectId": "project-xxxxx",
  "sourceNodeId": "node-source-xxxxx",
  "sourceWorkspace": {"kind": "managed_run", "workspaceId": "workspace-source-xxxxx", "generation": 1},
  "layoutVersion": 1,
  "scopes": [
    {
      "scopeId": "repo-xxxxx",
      "mountPath": "repository-xxxxx",
      "generation": 1,
      "baseCommit": "<完整Git SHA>",
      "coverage": "repository",
      "policyVersion": 1,
      "policyHash": "<规范化文件选择策略的SHA256>",
      "entries": [
        {"path": "src/example.js", "operation": "upsert", "hash": "<SHA256>", "size": 120, "executable": false},
        {"path": "src/obsolete.js", "operation": "delete"}
      ],
      "expectedTreeDigest": "<最终纳入范围的文件清单摘要>"
    }
  ],
  "expectedWorkspaceDigest": "<逐仓库摘要与目录布局的规范化SHA256>",
  "inputSetId": "<规范化契约的SHA256>"
}
```

其中 `<...>` 是示意占位，实际调用必须填写真实值。多仓库任务在同一输入集合中逐仓库指定 baseCommit，不能只记录一个仓库的版本。

`entries` 表示相对于该 baseCommit 的完整覆盖层；未列入修改或删除的基线文件继续从基础提交获取。它必须覆盖本次执行所依赖的已保存变动，包括符合范围规则的新增未跟踪文件。

### 4.3 哈希计算

inputSetId 根据规范化契约计算，包括 schemaVersion、digestVersion、kind、projectId、sourceNodeId、sourceWorkspace 的稳定身份与 generation、layoutVersion、各 scopeId/generation/mountPath、baseCommit、coverage、policyVersion/policyHash、排序后的 entries 和 expectedTreeDigest，以及 expectedWorkspaceDigest。declared_paths 模式还包括排序后的 declaredPaths。不包括创建时间、请求编号、机器绝对路径和后续状态。

本稿只采用 digestVersion=1：最终文件树使用第 4.7 节的完整文件列表 SHA256，输入契约使用本节 canonical JSON。版本号进入 inputSetId 并出现在准备回执；未知版本拒绝，不自动降级。现有 source-sync 的 manifestDigest 使用不同结构与排序、可包含 tombstone，不能用于 expectedTreeDigest 或相互换算。base tree OID＋覆盖层摘要可作辅助索引，但不在本稿代替最终树摘要；若未来采用，另增版本并重新评审。

规则如下：

1. 使用 UTF-8 与固定的 canonical JSON 编码，无 BOM、无额外空白和末尾换行。对象键按 Unicode 码点排序，不使用受语言区域影响的排序，也不直接以 JavaScript 默认 UTF-16 排序代替。仅待计算的 inputSetId 字段本身排除；文件 hash、policyHash、expectedTreeDigest 和 expectedWorkspaceDigest 都参与 inputSetId 计算。
2. scopes 按 scopeId 排序，entries 按 path 排序，重复 scope 或路径拒绝；generation、size 等数字只接受非负安全整数。可选字段采用固定的省略规则，不能把省略与 null 混用；跨语言实现必须通过同一组字节级测试向量。
3. 路径保持源端文件名的原始表示，不擅自更改 Unicode 或大小写；无法以合法 Unicode 标量和 UTF-8 无损表达的名称拒绝，目标文件系统兼容性另行检查。对象规范编码不得因数字样式键的枚举顺序改变输出，字符串使用固定 JSON 转义规则。
4. 文件哈希基于原始字节，不转换换行、编码或内容。
5. 路径、删除操作、可执行位、基础提交任何一个变化，都产生不同的输入身份。
6. 原内容不变但 mtime 改变，不产生不同的内容身份。

字符串规范编码固定转义引号、反斜杠及 C0 控制字符：五种标准控制字符使用 JSON 短转义，其余使用小写十六进制 Unicode 转义；其余合法字符直接编码为 UTF-8，不额外转义斜杠。整数不带指数或前导零，禁止负零、非整数和超出安全范围的值；布尔值固定为 true/false。空字段按 schema 固定省略，不能在一端省略、另一端填 null。编码验收需要包含非 BMP 字符、数字样式键和空/删除覆盖层的共同向量。

blob 按文件内容哈希复用；即便两份输入因设备或范围身份不同而 inputSetId 不同，相同文件字节仍可复用。任务命令、验收标准和运行环境不塞进代码快照哈希，分别记录在执行请求及结果中。

### 4.4 Git 基础版本的可用性

源端和目标端必须能够读取固定的 baseCommit。目标端已有 Git 对象时直接复用；缺少时沿用已授权的仓库获取或 Git 交付入口，不隐式切换到目标端旧 HEAD。

若取得该基础版本需要新的发布、凭据或审批，状态应明确为 waiting_base_commit 或 needs_input。快照编号不会绕过 Git 托管权限和原有交付审批。

基础 Git 对象和使用中的输入集合要有保留引用，防止目录回收或 Git GC 使已记录的任务无法重建。

### 4.5 真实源工作区定位

源定位请求包含 sourceNodeId、sourceWorkspace 以及需要的 scope 列表。sourceWorkspace 有两种明确类型：

| 类型 | 请求引用 | Worker 实际解析 |
| --- | --- | --- |
| managed_run | sourceRunId、workspaceId、workspace generation | 该 Run 登记且获准读取的实际开发 worktree；各仓库来自该工作区的 repository 映射 |
| bound_project | workspaceId、workspace generation | 该设备当前明确绑定的普通项目目录；必须由请求明确选择，不作为 managed_run 失败后的默认回退 |

sourceRunId 是来源与权限证据，保存在冻结操作记录；它不进入 inputSetId 的内容规范化字段。同一工作区中的后续 Run 可以引用同一份字节输入。workspaceId/generation 则进入输入身份，防止重绑目录后混用旧来源。

Home 核对项目、设备、Run、scope 和读取授权，源 Worker 核对本地登记的实际路径、目录存在性、仓库归属及工作区 generation。客户端任意绝对路径不作为信任依据，原生 Agent 无权伪造 workspace 身份。

workspaceId/generation 是 Worker 对实际目录登记的稳定身份。旧 Run 若只有路径字段，先在当前设备验证目录存在、拥有者、项目和 repository 映射，再建立兼容登记；缺少证据则明确阻塞。兼容登记不修改旧 Run 或强塞其他设备的原生会话。

开发 worktree 已删除、设备不符、scope 不属于它或绑定已变化时，分别返回 source_workspace_missing、source_workspace_mismatch 或 configuration_changed。错误携带可定位的来源引用，不自动读取普通项目旧 HEAD。

源工作区仍有受管写入时等待其自然到达可采集窗口；外部写入导致输入持续变化时有限重试后 source_changing。源目录租约只协调平台管理的写入，不声称能阻止任意外部编辑器。

file_set 依赖本次范围/工作区读取授权，不要求该项目先启用 continuous 同步。已有后台同步可预热相同内容；新快跑不会为了取得输入而自动改变普通目录同步的启用范围。

### 4.6 多仓库目录布局

mountPath 是相对任务根目录的位置，例子只使用逻辑路径 repository-xxxxx；禁止绝对路径、父目录跳转、符号链接路径、重复位置及跨 scope 文件/目录冲突。首次单仓使用已登记的仓库 key，Worker 返回实际目标映射。

多仓库启用前冻结完整 layout。原跨仓库相对引用需要通过 layout 保持或明确的任务配置重建，不能只靠每个仓库哈希相等证明应用可运行。包含关系仅允许显式的容器 scope 与排除规则，不能让两个 scope 拥有同一文件。目标端同时检查跨 scope 的大小写、Unicode 别名和父路径碰撞。

layout 与逐仓库 input 都固定到输入身份；改变布局要产生新的输入集合与准备记录。多个 scope 一并发布为一个 inputSetId，但来源一致性仍是第 5 节规定的已观察字节集合，不声称各仓库来自同一精确瞬间。

### 4.7 最终文件摘要与上下文材料

repository 覆盖的期望执行树按以下确定性规则计算：

1. 从 baseCommit 取得完整候选基线树；按不可变 policyHash 对应的已支持策略选择执行输入路径。
2. 对允许路径应用完整覆盖层。upsert 替换或新增；delete 从最终文件树移除，删除指令本身仍保存在 entries 中。
3. 每个最终文件表示为 [path, SHA256, size, executable]，path 按第 4.3 节相同的 Unicode 码点规则排序。expectedTreeDigest 是该列表 canonical JSON 字节的 SHA256；所有未修改但纳入执行范围的基线文件也在列表内。
4. 目标端依据实际检出并应用后的字节重新计算，不能拿收到的 manifest 自证正确。缺失、额外纳入范围的文件或内容/权限差异均使准备失败；每个必要 scope 和 context 均校验完成才能发布 input_ready，缺一个 blob 也不能部分 ready。
5. expectedWorkspaceDigest 是按 scopeId 排序的 [scopeId, mountPath, expectedTreeDigest] 列表的 canonical JSON SHA256。input_ready 同时返回逐 scope 实测摘要与聚合 verifiedDigest。

文件选择策略至少固定强制排除、scope 嵌套关系、允许的文件类型和 coverage。policyHash 对应正文需要可取回并受平台支持；旧 Worker 不认识策略时 unsupported，不信任发送方自行放宽。declared_paths 另外明确纳入路径及依赖声明；首次版本不支持该模式。

只有明确策略允许排除的内容才能不进入输入。符合执行范围的必要文件超过单文件、批次或总量限制时，返回 input_limit_exceeded 并列出合法范围内的阻塞路径和限制；不截断、按体积猜测“不是源码”或跳过后生成成功快照。被 ignore 但构建所需的配置/资源必须纳入获准输入，或以已登记目标端生成步骤产生并留证；无法满足则 input_scope_incomplete。生成的依赖/产物进入 runtimePaths，不能以生成步骤替代缺失必要源码；密钥仅走第 5.4 节环境入口。

使用 git worktree 检出后，平台必须处理被策略排除的跟踪文件，而不是让它们悄悄成为未校验输入。Git 元数据是工作区管理信息；依赖与产物位于登记的 runtimePaths。必需的源码/配置落在排除范围时返回 input_scope_incomplete，必要环境配置通过目标设备获准环境入口提供。Git 属性或检出转换导致目标实际字节无法匹配时返回 checkout_content_mismatch，不能静默忽略。

Worker 不再从目标普通目录任意复制 AGENTS.md、CLAUDE.md 和共享文档充当本轮材料。任务请求登记使用哪些指令与文档及其源工作区、路径、哈希和大小；准备时复用同一 blob 传输并固定为 contextRefs。它们按同一 digestVersion 形成单独的 contextDigest，记录在执行请求、准备回执和报告中，保持代码 inputSetId 与执行上下文的职责区分。

每条 contextRef 的摘要行固定为 [sourceNodeId, scopeId, workspaceKind, workspaceId, workspaceGeneration, scopeGeneration, path, targetPath, hash, size, executable]，按前述六项来源身份、path、targetPath 的码点/整数顺序排序；contextDigest 为包含 digestVersion=1 和该 contextRefs 行列表的对象的 canonical JSON SHA256。目标路径是任务根内的固定相对路径；重复映射拒绝，空列表亦有明确摘要。Worker 校验合法来源和目标实际字节后计算相同摘要，不能只回显源端列表；角色提示词/运行配置仍在执行请求单独登记版本，不混入文件上下文哈希。

源工作区已有且本轮 CLI 需要加载的 AGENTS.md/CLAUDE.md 按上述方式固定；可选共享文档按需登记，旧 handoff 不全量注入。上下文材料仍受同一读取授权、路径和内容校验，不允许借 contextRefs 传递排除的凭据或运行数据库。context 与代码树映射到同一物理路径时必须引用相同字节；冲突则 context_path_collision，不覆盖固定代码。指令文本、角色配置、目标运行配置由执行请求保存版本引用或摘要。配置变化只影响新请求。

## 5 输入范围与冻结一致性

### 5.1 默认采用完整仓库输入

通用代码执行默认使用 `coverage=repository`：确定基础提交，并采集该仓库允许范围内相对基线的全部必要变动。锁文件、构建配置、测试配置、资源和间接源码依赖不能遗漏。

只有任务确实被限定为独立脚本或声明了可验证的依赖集合时，才使用 `coverage=declared_paths`。对于未知依赖，不假装能自动推导完整闭包；应扩大到相关仓库或返回 input_scope_incomplete。

跨仓库引用需要纳入相关 scope。首次实现不自动支持 Git submodule、Git LFS 指针还原、符号链接或任意仓库外依赖；遇到时返回明确的不支持原因，不能把缺失内容当作空文件继续执行。

### 5.2 源端冻结步骤

1. 校验范围绑定、generation、策略版本和读取权限。
2. 与该范围的受管写入协调，等待安全的采集窗口；不能中断正在运行的 CLI。
3. 固定 baseCommit/tree OID、当前 HEAD 和索引观察标记。候选集合为 baseCommit→当前 HEAD 的已提交路径差异，与当前 HEAD→索引→工作区的修改/新增/删除/权限差异、获准未跟踪路径的并集；重命名用旧路径 delete＋新路径 upsert 表达。只查 git status 会漏掉基准以来已提交的变化，不能作为完整覆盖层证明。
4. 读取实际字节并计算哈希；对需要执行的输入，不直接相信 watcher、mtime 缓存或旧目录同步摘要。
5. 检查采集前后 HEAD、索引观察标记和路径集合，并再次稳定读取可变输入字节/权限，核对第一次采集哈希。Git status 相同不证明字节相同；assume-unchanged、skip-worktree、忽略规则、检出转换等不得使必要跟踪路径漏检，不能证明完整性时扩大实际核对或返回 unsupported/input_scope_incomplete。有变化则放弃候选，在有限次数内重采；持续变化返回 source_changing。
6. 将内容写入不可变缓存，校验后原子发布输入清单及 inputSetId；保留实际 sourceWorkspace/sourceRunId、捕获起止时间、观察策略与一致性等级的冻结回执。

候选发现与最终树证明分开：基线 blob 的字节 SHA256 可以按仓库对象库身份、对象格式、tree/blob OID 和 digestVersion 缓存，经验证的不可变对象不必每轮重新读取；策略过滤和最终清单仍按本次固定规则重建。可变工作区的最终必要路径不能仅凭索引缓存判未变，需要实际字节校验，必要时完整枚举/核对。现有 captureSourceSnapshot 只支持其 HEAD 基线约束，不能直接用于旧 baseCommit＋新 HEAD 而沿用旧拒绝/漏采行为；file_set 需独立实现完整差异采集，不改变普通同步规则或用户索引。

普通文件读取无法提供针对任意外部编辑器的全目录事务快照。无受管静默窗口或文件系统原子快照时，能承诺的是“保存这次读取并验证过的字节集合”，不能宣称是某个精确瞬间的整个应用状态；这类快跑结果不得升级为正式一致性验收。

源码仍在频繁变更、用户要求严格一致时，应等待写入者自然结束或采用固定 commit 流程。不得为了冻结输入自动停止其他任务。

首次冻结回执的 captureConsistency 固定为 observed_bytes，并记录 managedWritersSettled。单个文件使用稳定字节读取，完整范围用采集前后核对与有限重试；最多三次候选采集，耗时上限由请求预算给出。无法完成时保留原因，不发布半份 ready 输入。文件系统原子快照只有实际支持且另行验收后才增加相应等级。

### 5.3 源码与运行环境分开

代码快照不携带账号登录态、密钥、数据库文件或原生 CLI 会话。目标设备的凭据按第 5.4 节用途单独选择，不把普通开发 Run 的全部授权默认继承给 S/测试，不写入 manifest、日志或提示词。

依赖安装依据锁文件和目标平台完成。记录 OS、CPU 架构、运行时版本、包管理器版本、锁文件哈希、依赖安装方式及所用测试数据。相同代码快照不保证服务器和 Mac 的运行环境相同。

macOS 目标必须检查大小写不敏感文件系统下的路径碰撞、Unicode 名称兼容性及可执行权限。发现不能无损还原的输入时拒绝准备，不静默改名。

### 5.4 准备凭据与执行凭据隔离

现有普通 Agent 启动可注入 Git Hosting 凭据；不能把现有启动路径原样复用后声称 S/测试无 push 凭据。

- baseCommit 准备优先复用本机已校验对象；缺失对象只经获准的 fetch/交付入口取得。准备 action 使用按仓库限制的只读凭据引用；仅有发布凭据或需要新交付批准时等待，不向快跑 CLI 转交该凭据。操作结果保存来源与对象身份，不保存认证正文。
- S/测试执行入口不调用普通开发的 Hosting 注入逻辑，不继承其 Authorization extraHeader、凭据 helper 或 Git 配置文件引用；构造任务专属、按用途允许的环境。准备结束不遗留本轮 token 到共享 Git 配置、快照或执行目录，日志/产物不暴露凭据。
- 模型账号登录、获准依赖下载和测试环境访问分别引用目标设备的私有配置，记录用途与配置版本，不复制源端账号。测试数据及业务写入仍需各自授权；不更改设备全局 Git/CLI 登录配置来实现隔离，以免影响其他任务。
- 首期的承诺是“平台不向 S/测试注入发布凭据”，不等于在同一用户账号下实现了操作系统级密钥隔离。已有本机 Git helper、SSH agent、CLI 插件或可读用户配置可能具有额外能力，执行前核查并标明限制；要求严格不可访问发布凭据时，只有经过验收的受限账号/进程隔离环境可以运行，否则 unsupported_credential_isolation，不以提示词作为隔离证明。

凭据策略随执行请求固定，准备端只读获取与执行端实际环境各自验收。必要凭据不存在或最小权限无法满足时返回 needs_input，不擅自复制 token、提高权限或改派设备。

### 5.5 独立审核可见性贯穿读取

Home 对发起 Run 的身份、reviewGuarded、项目/路径权限及已公开文档基线先做审核可见性校验；Worker 的实际路径/范围校验不能替代 Home 的审核隔离。沿用现有 reviewDocumentAllowed 等规则，新入口不能让某审核者提前读取其他人的未公开意见。

file.read、缓存命中、路径落盘、contextRefs、input.freeze/prepare、交接卡和产物读取都保留调用者与合法来源链。一个 hash 存在或缓存已有字节不表示此调用者获准获取；查询、正文、清单及错误返回均不得泄漏受限报告，使用通用 denied 或脱敏阻塞说明。缓存可以按字节去重，但授权引用按项目/Run/可见性分别核验。

准备执行目录时也只能带入该角色获准的输入和上下文。不能先落入本地文件再靠页面隐藏实现隔离；审核材料若无法从普通工作区中安全排除或读权限无法证明，阻塞该角色准备，不能把其他审核正文放进其可读目录。公开/解锁由现有审核策略决定，不增加自动公开入口。上述保证限定于新增平台入口及其提供的准备内容；同用户原生 CLI 对其他本机目录、Git 对象库的访问不因 reviewGuarded 自动隔离。要求这类强隔离时需获准且已验收的隔离运行环境，否则 unsupported_review_isolation，不作未经证实的保密承诺。

## 6 服务器修改后在 Mac 执行的完整流程

```text
服务器保存文件
    ↓
确定任务类型、范围和基础 Git 版本
    ↓
源 Worker 冻结输入 S1
    ↓
Mac 获取基础版本及缺失内容
    ↓
建立隔离目录、应用覆盖层、校验实际文件
    ↓
返回 S1 的准备回执
    ↓
检查执行授权、环境和资源占用
    ↓
在该目录执行并回传结果
```

### 6.1 请求

用户表达“在 Mac 上测试服务器刚保存的版本”。总管或确定性的路由入口明确填写 sourceNodeId、sourceWorkspace/sourceRunId、targetNodeId、输入范围、S/G 类型、要执行的任务和可接受的副作用。来源是某个开发任务时必须绑定该任务的实际 worktree；来源是普通项目目录时明确选择 bound_project。任务文字不能替代实际设备字段。

用户只要求“读一下文件”时采用 F，不自动启动服务或执行代码。

### 6.2 冻结及传输

源 Worker 创建 S1。Home 保存不可变输入引用，通知 Mac 准备。Mac 先查询本机内容缓存，只获取缺失 blob；已有内容仍校验尺寸和哈希。

后台同步如果已经把内容送到 Mac，可以减少传输，但不能直接把普通项目目录当作已准备好的执行目录。任务不等待无关 scope 或离线第三台设备。

### 6.3 本机准备

Mac 先取得空间预留与 preparation 写入租约，再在项目内的登记任务目录按 layout 创建隔离 worktree，检出 baseCommit，按不可变策略与 manifest 应用修改及删除。准备过程中使用 staging 状态，全部必要 scope、blob、上下文及布局验收完成后才标记 ready；首期只开放单仓，不代表未来多仓可按部分成功启动。

目标端计算各 scope 最终纳入范围的实际文件清单摘要，与 expectedTreeDigest 对齐，再计算聚合 verifiedDigest 与 expectedWorkspaceDigest 对齐，并返回 preparationId、inputSetId、设备、scope generations、实际目录映射、contextDigest、完整性检查方式和有效准备租约。不能由模型回复“文件已经同步”来代替此回执。

### 6.4 执行前再检查

Worker 验证：

- 准备回执属于当前项目、目标设备与输入集合，状态仍 ready。
- 设备和范围绑定未变化，工作目录仍存在且属于本任务。
- 任务未取消，目录租约与环境准备没有失效。
- 当前并发容量允许启动，不与已有终端或测试服务冲突。
- 输入在准备后没有被其他操作改写。

首次运行目录提供独占任务根、受管写入协调、不纳入连续同步和执行前后实际字节摘要校验；integrityProtection 标记为 exclusive_before_after。这是本次固定输入的准备与前后检查证据，不能声称操作系统级不可变执行。外部程序可能修改后恢复原内容，前后摘要无法证明没有发生过此类短暂变化。已观察到的源码写入事件也要纳入检查；发现运行期间被修改时标记 input_mutated，禁止通过。只读挂载或更强进程隔离需要另行实现，未具备时强一致要求转入 G 或返回 unsupported_integrity_requirement。

### 6.5 原生会话、准备与执行身份

角色的聊天历史保留原身份。原生执行会话增加 executionContextId 绑定，程序核对 inputSetId、preparationId、workspaceId、contextDigest、设备、CLI 和账号身份，而不是仅按角色名称复用旧目录。

首次 task.execute 原子认领 preparationId，创建一个 executionContextId；该 preparation 不得由无关请求再认领为另一个执行环境。同 requestId 的规范化重试取得原 executionContext；相同输入的另一次独立快跑创建新的 preparation，blob 与 Git 对象可复用。

同一 executionContext 内的合法继续回合可恢复原生会话，前提是原会话真实 idle、目录及输入检查通过、没有未知进程与配置身份变化。不同角色使用各自原生会话，环境交接按第 8.5 节执行。

S2、不同 preparation 或新的实际目录默认创建新的执行原生会话，保存 predecessor 关系并按需带入短交接摘要。保留旧平台历史及原生历史，不把旧 nativeSessionId/resumeWorkspace 填入新上下文，不改写 S1 的目录。相同代码 inputSetId 也不能证明旧可写执行目录无污染。

Run 发起前已由程序选定并登记准备目录，Worker 的 continuation/resumeWorkspace/普通工作区优先级必须服从当前 executionContext 的匹配校验。旧会话不匹配时不应先打开它再尝试覆盖层。未知占用进入 reconciling；不通过新开一个进程绕过原占用。

### 6.6 执行及回报

Worker 使用明确的任务目录、目标环境和输入引用启动 Agent 或已获准的命名执行动作。任务在运行过程中继续引用 S1，不能自动切换到服务器后来保存的 S2。

报告至少记录任务身份、基础 SHA、inputSetId/preparationId/executionContextId、实际目录映射、contextDigest、captureConsistency/integrityProtection、输入前后校验、环境、执行命令或动作、退出状态、测试结论及证据路径。运行成功与测试通过分开记录。

### 6.7 用户继续修改

源端再保存生成 S2，不修改 S1。默认保留正在执行的 S1 任务。用户明确要求重测 S2 时创建新的执行请求；只有尚未启动且允许被替换的排队请求才能受控取消，不能自动停止已运行任务。

普通源绑定或策略 generation 变化使尚未认领的旧准备失效，不把正在运行的 executionContext 改绑到新目录、不重新应用覆盖层、不自动终止其 CLI。现有运行保留原输入与授权快照；后续新启动或继续回合需要核对当前有效授权、本地输入及该上下文身份，不能仅凭源设备新 HEAD 自动换版本。明确的任务取消或权限撤销按平台既有规则另行处理。

## 7 本机结果如何返回服务器

测试输出作为独立产物回传，包括测试报告、日志摘要、截图、覆盖率和用户明确需要的构建产物。记录 sourceRunId、inputSetId、产物路径、哈希和大小，报告链接指向可读取的证据。

不把整个 Mac 工作目录反向同步到服务器，不把 node_modules、临时文件或测试生成的配置覆盖到原项目。测试发现问题后，返回可定位的失败证据，由开发角色在获准工作区修改并产生 S2 或新 Git commit。

如果用户另行授权测试角色修代码，该任务应转为明确的开发任务，声明写入范围和新输出身份；不能继续以“只读测试”名义修改。快跑结果提升为 G 时需核对新 commit 对应内容，并重新履行必要审核和正式测试，不自动沿用 S 的 passed。

多个开发 Agent 并行修改时，分别保存输出分支或输出快照，由明确的整合者执行 Git 合并与冲突处理。本稿不提供自动文件拼接或最后写入者覆盖。

## 8 执行目录与资源占用

### 8.1 不按 Agent 永久复制项目

工作目录按实际任务分配。Q/F 不创建 Agent 执行工作目录，F 可以复用普通同步副本或按哈希保存的受控内容缓存；S/G 才创建需要的执行目录。角色可保留自己的会话历史，但会话身份不等于永久保留一套源码副本。

同机 Git worktree 共享 Git 对象数据库，检出的普通工作文件仍会占用空间。内容缓存按哈希复用；支持时可采用写时复制，不支持就使用普通复制。禁止通过可写硬链接让不同任务共用源码 inode。

多个纯读取消费者可以复用不可变内容缓存。不同 executionContext 的 Agent CLI、构建和测试默认获得独立目录；同一 executionContext 内的 Mac 环境协助和测试按租约顺序使用已准备的环境，不重复检出源码。各 Run 的临时文件与产物仍独立，不能因为角色叫“审核”就假定其工具绝不会写文件。

### 8.2 依赖与产物

- 可以复用包管理器下载缓存或有哈希/平台身份且实际不可变的依赖制品；不让多个任务直接共享可写 node_modules。普通软链接或硬链接不是只读证明，不能把共享可写 inode 当安全热复用。
- 环境复用按 OS、架构、运行时、包管理器和锁文件身份匹配，避免把 Linux 依赖复制给 Mac。
- 构建缓存必须有正确版本键；不能因为目录名相同就复用旧产物。
- 测试临时文件与日志进入任务专属产物目录，限制单项及总量，超限明确报告。
- 代码版本相同不代表数据库、浏览器登录态或测试数据相同，报告必须分开说明。

依赖安装必须采用目标包管理器的锁文件固定模式；缺少锁文件、平台不支持锁定安装或解析需要更新锁文件时，返回 dependency_not_reproducible/input_write_required，不能静默改输入。安装脚本、构建、快照更新同样受输入保护；依赖成功不等于测试通过。

protectedPaths 是本次纳入的基线/覆盖层文件及固定上下文，包含跟踪锁文件、配置、测试源码与测试快照；runtimePaths 只登记获准依赖、临时文件、构建和测试产物，可用明确忽略目录或任务外置位置，不能与 protectedPaths 重叠、借符号链接越界或通过父目录豁免保护文件。Git 管理元数据不计入源码树；未跟踪必要源码是否受保护由输入契约决定，不能只靠 Git tracked 判断。

执行前后对 protectedPaths 做实际字节/权限与完整路径检查，并结合已观察写入；正常 runtimePaths 安装/构建不误报 input_mutated。工具预先声明需要写保护文件时返回 input_write_required；实际改写则 input_mutated，不判通过，由新开发任务处理。不能为构建成功临时扩大忽略策略；前后校验的检测能力仍受第 6.4 节限制。

### 8.3 读取与重试开销

复用主线程同步恢复修复的协议原则，并在新输入契约中继续保证：

1. 先用索引选择到期、可发送的小批元数据，再按需读取正文。
2. 不每半秒加载所有历史回执或完整 manifest；无工作时降低唤醒频率。
3. 不让未就绪或冷却中的队列前部记录阻塞后面的可发送记录。
4. 相同输入引用和相同命令去重；暂时故障指数式或分段退避，永久错误停止盲试。
5. 未知写入结果保留为 reconciling，不为了腾空队列改成成功。
6. 扫描缓存只用于候选变化发现；freeze、apply 和输入完整性验收使用实际字节。
7. 普通保存继续触发后台增量同步；空闲时处理积压，但不以“空闲”为由重复全量采集。F 仅触发指定路径核对与必要内容补齐，不能等待或创建无关整仓批次。

建议初始上限为单设备同时一个输入准备任务，回执选择每批不超过 16 条，恢复性上传一次一个。暂时失败使用 5、15、30、60、300 秒的间隔；自动恢复尝试最多五次后转为等待恢复或人工处理。工作传输的数量和字节上限沿用已部署范围政策，不在新入口悄悄扩大。具体默认值需在实现和实机测试中校准。

### 8.4 回收规则

本次首次上线默认保留旧目录、历史和证据，不自动清理现有数据。新建准备目录从创建之初登记 owner、输入引用、空间预留与可回收条件；达到配额后排队，不继续无上限创建。未来开启任务目录回收，必须同时满足进程已退出、无终端接管、无会话恢复依赖、产物已保存、输入仍可重建、没有未交付修改或未解决冲突。

先实现引用统计和“可回收”提示，再提供明确启用的自动策略。不得把冲突版本、活跃输入、回滚证据或唯一未提交副本作为普通 LRU 缓存删除。保留窗口内的输入需要保留完整重建依赖；若以后获准释放内容，只能标记历史“证据保留但不可重建”，不能继续宣称可恢复执行环境。

### 8.5 执行环境与服务交接协议

一个 executionContext 对应一个实际准备目录和固定输入；拥有准备写入租约不等于已经执行。task.execute 通过原子 claim 把该准备绑定到一个执行上下文，校验尚无其他上下文认领。新请求需要独立快跑时新建准备记录；受支持的同上下文继续执行与环境协助则引用原 executionContextId。

目录租约记录 projectId、workspaceId、preparationId、executionContextId、holder、leaseEpoch、expiresAt、状态及 commandId。source、preparation、execution 三种用途明确分开。准备写入完成后，租约在 Worker 对账成功后转为本上下文执行使用；不能用一份聊天里的“交接完成”替代程序接收。

environmentServices 记录输入身份、实际 cwd、上下文、服务地址、可核验启动身份、启动时刻、健康证据、producerRunId、consumerRefs、资源权重与租约。服务归 Worker 管理，producer Run 退出后消费者尚在使用时仍占用资源，不随 Agent 回合结束自动关闭。

逻辑操作为 service.start、service.acquire、service.release、service.status、service.stop 和 workspace.claim/renew/release。均由受支持的 Home/Worker 操作实现，使用 requestId 幂等与租约 epoch 校验。不是要求 Agent 现在调用这些尚未注册的命令。

交接顺序为：平台保存服务登记 → 接手方在原 executionContext 内核对输入、地址和状态 → 原子登记 consumerRef 并取得接收回执 → 原持有者释放自己的引用。服务进程通常继续由原 Worker 控制，不把 kill 权限交给消息里任意接手者。

首期同时只有一个目录写入者。准备、依赖安装和构建在顺序写入阶段完成；测试读取已准备的环境，服务的运行产物进入 runtimePaths。确需写输入时必须改为新的开发操作。服务与测试共用同一环境不是授权两个 CLI 同时写同一源码目录。

旧 leaseEpoch 的续租、释放、取消和服务停止请求均不能作用于新持有者。Home 重启后从持久记录恢复 epoch，不从零重新认领；Worker 以实际启动身份对账。租约到期只禁止新启动与新认领，不能单凭时间把仍在运行或状态未知的进程判为已退出。

服务仅在所有消费者释放、无有效持有者、无未知执行状态且该进程确由本上下文创建时允许关闭。端口冲突选择新的获准端口或阻塞，不结束其他进程。Worker 离线时保留未知占用，待重连核验；不腾出容量启动第二份相同服务。

service.stop 必须核对本上下文所有权、当前 leaseEpoch、零消费者、实际启动身份和已知执行状态；停止/回收结果持久保存。CLI 退出不代表其启动的后台服务已退出，不能只按 PID、端口或租约到期杀进程。首期 P3 限同一执行上下文、单轮内受 Worker 登记管理的服务，并在结束时确认本任务服务已回收；未知结果保持占用并阻塞新认领。跨轮存活或交给其他角色须待 P4 的消费者/租约恢复机制验收后开放，不能提前用聊天卡绕过。

交接证据是认证通道保存的结构化 Worker 记录，包含 task/executionContext、input、leaseEpoch、launch 身份和实际消费确认。CLI 日志是数据，不能冒充系统回执；XML 标签不提供鉴权，使用时需转义。本文不假定已经有签名/沙箱能力，不能让模型信任一段伪造的“系统签名”。

浏览器测试绑定服务登记与 executionContext，不仅保存一个 URL。验收证据需要说明监听进程、实际 cwd、启动/构建记录和目标地址的对应关系，防止测试落到旧服务或其他任务环境。

### 8.6 首次上线的空间预算

配额与引用登记随 P2/P3 上线，不等待 P5。下列值是供试点采用的设计默认值，实施时通过实机验证校准；不修改既有普通角色的并发配置。

| 项目 | 首次设计值 |
| --- | --- |
| 同设备 S 输入准备 | 一次一个；其他请求在平台队列等待 |
| 同设备 S 执行环境 | 默认一个；服务仍在使用或进程未知时继续占名额，并受既有 Worker 并发门禁约束 |
| 每设备新 S 准备目录 | 最多四个未回收目录，包含失败 staging；旧目录不因此被删除 |
| 新 S 物理增量预算 | 每设备合计 8 GiB，包含新增 Git 对象、blob、检出文件、依赖及产物；普通既有目录不作自动清理对象 |
| 宿主空闲空间保留 | 至少 5 GiB，并满足本轮 base 检出、依赖、缺失 blob 与产物的空间预留 |
| 单执行产物预算 | 合计 1 GiB；更大产物需任务明确声明并取得可用预算 |
| 源文件与传输范围 | 沿用当前已授权的文件/批次/路径限制；不借新入口扩大 |

Git 对象、blob、工作文件、依赖和产物分开计量：对象与 blob 只计一次物理占用；准备目录中的普通文件和依赖仍计其实际占用。写时复制只能作为实测支持的优化，不在未支持的文件系统上宣称零空间副本。

resourceReservations 保存设备、execution/preparation、预计增量、已观察占用、预留到期时间与状态。预留必须在同设备所有项目间原子扣减，两个准备不能同时使用同一份可用空间。预计依赖体积未知时 recipe 声明安装预算，并在安装前后检查实际空间；不足时 waiting_quota 或 insufficient_disk，不继续新步骤。

源端冻结与 Home 内容接收也需要预留新增 blob 空间，不能在目标准备已被配额阻塞后继续无限生成输入正文。相同 blob 复用后退回多预留的空间；取消但尚未回收的实体仍计入占用。预留超时只有在核实未开始实体写入时才可自动退回；已有文件、目录或未知结果保留占用并对账。

配额首次以平台准备、上传及产物入口计量和分阶段核对实现，并非操作系统对任意外部 CLI 的磁盘硬隔离。空间突降时停止新的准备与大文件写入入口，保留已有任务和证据；不会为了达标杀其他任务。产物入口超限停止接收新增内容并记录截断/失败，不能把残缺证据写成完整产物。

回收提示同时列出无活跃引用、无进程、已保存产物且输入可重建的新目录。首次不自动删除；即使全部不可回收，配额也阻止继续扩张。后续自动回收只针对显式启用策略后的登记临时目录，保留第 8.4 节的恢复保护。

### 8.7 后台观察与前台读取调度

后台采用按路径的候选索引，保存文件身份、size、mode、mtime/ctime 与已观察哈希。该索引仅发现候选变化，不替代 freeze、接收和执行前后实际字节验证，也不成为 source_current 的唯一新鲜度证据。

普通文件事件合并后只核对相关路径；新增/删除目录核对相关子树；文件名未知、策略或忽略规则变化时安排有界重新枚举。通知遗漏通过分块轮询核对目录与候选元数据，另行安排完整字节补偿轮次。处理一次普通保存不应默认重新读取整个仓库。

补偿轮次按 scope 轮转、每块最多 64 路径或 16 MiB 内容，块结束让出调度。设计默认五分钟为一个全范围补偿目标窗口；超过预算则显示扫描进度、最旧未核对时间和 degraded 状态，不假称都已最新。事件持续到达时可并行登记候选，传输仍按安全队列处理，不停后台同步。

设备共享 I/O 调度优先处理 Q/F 的短查询与指定路径，其次 S 准备与明确前台工作，再处理背景扫描/传输。大准备和扫描需要分块可让出；已有文件 apply 的原子/journal 小步骤先完成，不能被半途抢占。后台有可行动工作时给予定期小块份额，避免前台连续请求使其永久饥饿。

已有传输、源冻结与新 F/S 共用有界 I/O、连接和哈希工作预算，不能每个模块各自开启一套无上限并发。后台候选设计上限为每设备每秒 250 路径元数据核对及 16 MiB 哈希字节，允许调整；监测 CPU、I/O 与交互延迟后校准。原始 CPU 目标不通过隐藏队列、关闭 scope 或删除历史达成。

S 每次仍须完整必要范围核验，因此冻结成本与仓库规模有关。并发准备只限制 S 的准备槽，不把小 F 请求排到整份仓库准备结束以后；缓存损坏需要取回真实字节，返回具体等待原因。冻结被暂停、取消或失败时撤销其未发布 candidate，但保留可对账证据及已登记的空间占用。

## 9 状态机与回执语义

### 9.1 分别记录输入、资源与执行状态

| 对象 | 建议状态 | 说明 |
| --- | --- | --- |
| 冻结操作 | queued、collecting、ready、blocked、cancelled、reconciling | 操作记录与不可变输入分开；ready 才发布 fileInputSet |
| 目标准备 | queued、waiting_base_commit、waiting_quota、waiting_workspace、transferring、verifying、ready、blocked、cancelled、invalidated、reconciling | 输入、上下文与工作目录准备；未知写入结果先对账 |
| 执行上下文/服务 | claimed、active、waiting_consumer、reconciling、releasing、released | 持久资源占用，与 Agent Run 的结束分别记录 |
| 实际执行 | queued、starting、running、reconciling、succeeded、failed、interrupted | 复用现有 Run 生命周期，并关联 executionContextId |
| 测试结论 | passed、failed、blocked、needs_input | 与进程退出状态分别记录 |

设备 online 只说明通信存活，不等于环境就绪、任务空闲或测试通过。

### 9.2 三种确认

| 确认类型 | 证明什么 | 能否启动执行 |
| --- | --- | --- |
| delivery_ack | 指令或回执已可靠收到并保存 | 不能 |
| input_ready | 当前目标、范围、目录和输入身份校验一致，准备租约有效 | 满足其他运行门禁后可以 |
| run_result | 已执行任务的实际进程状态、测试结论和证据 | 用于结果判断，不能补造过去的准备过程 |

迟到回执可以标记 recorded_terminal，表示“保留了这份迟到证据”。它不改变原终态，不使原 cancelled/failed 自动变成 ready/succeeded，也不能满足下游依赖。

回执由目标 Worker 产生并被 Home 验证，不能允许 Agent 自报一个哈希就写入 ready。目录发生改变、租约失效、绑定 generation 变化或准备内容被回收后，原回执失效。input_ready 尚未认领时使用准备租约；task.execute 原子认领后返回执行租约，续用其 epoch。到期且仍有活进程或未知状态时保持 reconciling，不清空占用。

## 10 超时与恢复

| 场景 | 处理 | 禁止行为 |
| --- | --- | --- |
| 清单已保存但 HTTP 回复丢失 | 用原 commandId 查询或重放已保存证据，验证哈希后确认 | 把网络超时直接记成文件处理失败 |
| 取消的采集任务 | 发送采集取消结果，不引用不存在的写入上传回执 | 无限报 receipt_missing 后持续重发 |
| Home 已终结，Worker 回执迟到 | 验证归属并保存独立迟到证据，确认收件，保留原结论 | 用迟到消息覆盖原失败、取消或审核结果 |
| 文件写入途中断线 | 根据持久化 journal 核对已发生的效果 | 直接从头覆盖目标文件 |
| Worker 重启且原执行进程未知 | 核验已记录的进程身份、启动标记和租约，进入 reconciling | 仅凭低 CPU 或无新日志判死，再启动第二个进程 |
| 目标范围配置变化 | 使旧准备失效，要求重新解析与准备 | 把旧路径、旧 generation 静默用于新绑定 |
| Mac 离线或依赖缺失 | 保持等待或返回明确阻塞 | 悄悄改派服务器并称为本机测试 |
| 目标输入被改写 | invalidated/input_mutated，保留证据，要求新准备 | 继续给出固定输入的通过结论 |

不能承诺任意故障下的“绝对恰好执行一次”。实现目标是持久化去重、可靠对账和不盲目重启：在创建进程前登记 launch claim，使用可核验的启动身份；崩溃发生在登记与启动之间时，先查明是否启动，无法确定就等待处理。

取消作用于本次冻结/准备操作，不把已 ready 的 fileInputSet 全局改成 cancelled，也不撤销其他消费者的准备。Home/Worker 持久保存本操作取消与 epoch；每个后续写入块、发布 ready 或 launch 边界重查。收到取消后不得开始新写入，已进入原子/journal 步骤的效果先完成安全结算或回滚并对账，不虚称已经消失。重放只返回取消/历史证据，不续写 staging、不创建第二份准备、不发布迟到 ready。其他消费者可继续复用其获准共享 blob。旧 epoch 的已完成操作可以返回原历史回执，但不得重新施加释放、写入或启动副作用。

同一 requestId 与相同规范化参数重试，返回原操作；同一 requestId 携带不同参数，返回 request_conflict。用户明确要求再取最新代码或重新执行时，创建新请求，不能借重试语义返回旧快照冒充最新。

Q 查询要求新鲜数据时需新的采集尝试，不能把写入/执行的持久化幂等缓存直接套到查询结果。缓存命中必须带真实 observedAt、cachedAt 和 stale 状态。

## 11 拟议接口与持久化对象

### 11.1 操作契约

以下为逻辑操作名称，具体路由和 wb 命令在实现时注册；此稿不要求 Agent 调用尚不存在的命令。

| 操作 | 主要输入 | 输出 |
| --- | --- | --- |
| node.query | requestId、projectId、nodeId、recipeId/version、params、freshness | 结果、采集时间、数据源快照、截断说明 |
| file.read | requestId、projectId、sourceNodeId、sourceWorkspace、preferredReadNodeId、scopeId、path、freshness、expectHash | 实际文件哈希、大小、可执行位、正文或状态，以及源端、实际读取设备、observedAt、generation 和匹配/缓存证据 |
| file.materialize | requestId、projectId、targetNodeId、合法来源引用、目标已启用 scope/path/generation、expectHash、显式落盘授权 | 现有同步批次/路径操作引用、排队或冲突原因、实际落盘与基线/回执证据；不单独创建同步基线 |
| input.freeze | requestId、projectId、sourceNodeId、sourceWorkspace/sourceRunId、scopes、layout、contextPaths、coverage、采集预算 | freezeOperationId、inputSetId、来源与一致性回执 |
| input.prepare | requestId、projectId、inputSetId、targetNodeId、contextRefs、资源预算 | preparationId、预留、等待原因或 input_ready 回执 |
| input.status | projectId、freezeOperationId/inputSetId/preparationId | 当前状态、身份、可重建性和阻塞原因 |
| input.cancel | requestId、projectId、freezeOperationId/preparationId、期望租约 epoch | 本次操作取消或对账状态；不改写其他消费者的不可变输入 |
| task.execute | requestId、projectId、targetNodeId、preparationId、leaseEpoch、任务/已注册 recipe、授权和验收 | executionContextId、executionId、排队/运行状态 |
| task.result | executionId | 输入及上下文证据、环境、进程状态、完整性等级、结论、产物引用 |
| workspace.claim/renew/release | requestId、preparationId/executionContextId、holder、leaseEpoch | 原子认领/续租/释放回执 |
| service.start/acquire/release/status/stop | requestId、executionContextId、recipe/serviceId、consumerRef、leaseEpoch | 服务登记、进程身份、地址、使用者与占用状态 |

固定的确定性 recipe 由人登记并限制参数和权限；Agent 不能创建任意 shell/SQL 后门。Agent 自身工具执行仍受该任务的授权范围与实际运行权限约束。

`preferredReadNodeId` 只是获准副本的优先读取位置，不能改变源文件身份或增加访问权限。file.read 可返回 `readSource=replica|content_cache|source`；发生补齐时关联真实的路径级接收与校验证据。若接口退回源端读取，必须如实返回来源，不能声称已更新本机项目目录。

### 11.2 建议持久化对象

| 对象 | 保存内容 | 热路径读取 |
| --- | --- | --- |
| inputFreezeOperations | 请求归属、真实源工作区、捕获阶段、取消与对账 | 按设备/状态/到期时间选小批记录 |
| fileInputSets | ready 后的不可变代码契约、创建者、来源、一致性证据 | 小型身份摘要；清单正文按需读取 |
| inputPreparations | 目标、目录映射、contextRefs、阶段、租约、回执摘要 | 按目标与待处理状态索引 |
| executionContexts | 一次准备的执行认领、原生会话映射与资源使用者 | 按设备/活跃状态查询 |
| environmentServices | 启动身份、地址、输入、consumerRefs、持久资源权重 | 小型状态；不嵌入全部日志 |
| resourceReservations | 空间预留、准备槽/环境槽、实际占用及释放条件 | 同设备原子扣减与有限计量 |
| inputReferences | 活跃任务、会话恢复、报告与输入的引用 | 用于保护与可回收判断 |
| 现有 command/outbox | 指令身份、投递进度、重试时间 | 只读到期小批记录 |
| 现有 blob 存储 | 以内容哈希寻址的文件字节 | 按缺失哈希读取，不放入全量状态接口 |
| 现有 Run/报告/产物 | 关联输入、环境、业务结论与证据 | 页面按项目和分页请求 |

可在现有存储中扩展字段或对象，不另建一套消息总线。避免把 manifest、全部日志或文件正文重复嵌入每条命令及每次状态刷新。

### 11.3 兼容与硬门禁

新增入口分别声明 fileReadFreshness、fileMaterialization、queryRecipes、fileSetInputs、executionContextBinding、environmentLease、serviceConsumers、resourceReservations 等版本化 capability。Home、源 Worker 和目标 Worker 需要具备其实际操作依赖的能力；S 最小闭环依赖输入、目标认领、会话绑定与目录/资源管理全部就绪。多角色服务交接额外要求 serviceConsumers；P3 只允许单执行上下文、单轮内自有服务及核验回收，P4 才开放跨轮/多消费者交接。旧 Worker 不支持时明确返回 unsupported，不退回未校验的原目录执行。旧的 sourceInputs/sourceSyncBatchId 字段不视作 file_set 支持，现有 Git 通道的序列化和门禁保持独立。

保留现有 `directory_sync_is_not_git_delivery`。file_set 是独立输入类型，不伪装成 Git delivery，也不把目录同步批次填入正式 sourceSyncBatchId。

以下由程序执行硬校验：范围权限与审核可见性、generation、摘要版本与实际字节、全部必要 scope/context 完整、基础版本可用性、input_ready 归属、凭据用途、租约、任务取消、并发容量和写入冲突。提示词只辅助任务选择、解释与报告。

入口按 Q/F/S/G 做门禁映射。Q/F 默认读取不因原目录 dirty 或无关 apply 阻塞；明确普通目录落盘仍遵守同步写入门禁。S 使用独立的 input.freeze/prepare/task.execute 契约，不调用现有跨设备计划 execution_snapshot 路由来准备 file_set，也不添加全局 bypass 标记；S 核对当前准备树与覆盖层、实际目录冲突及共享设备资源，不用普通项目目录的 dirty 状态拒绝合法输入。普通目录同步的 apply_busy 不等同于独立准备目录正在写入。S 执行仍遵守已有明确的项目独占与设备并发规则；G 的原审批、clean、交付门禁不得为了 S 被删除。

### 11.4 Q recipe 首期白名单与管理

首期只把已核验的只读 action 包装成内置 recipe：workspace_check 的目录/HEAD 摘要与 cli_session_check 的指定受管会话检查；这两个名字对应已有 Worker action，但 node.query 的 recipe 注册/授权包装仍待实现。进程检查不得扩成 cli_session_stop、任意进程枚举或终端接管，文件正文走 F。其他查询先明确另行注册，不把“readOnly=true”作为任意 shell 的通行证。

内置注册表随代码发布，固定 recipeId/version、action、参数/返回 schema、目标能力、范围解析、是否只读、timeout、输出限额和脱敏规则。首期默认单次 5 秒、返回最多 100 条/256 KiB，可由已注册 recipe 设置更低上限；超时与截断如实返回，不杀其他任务。请求只带 recipeId/version 和经过 schema 校验的参数，不允许传 shell/SQL 原文、动态 action、任意绝对路径或扩展命令参数。

启用配置复用现有项目/设备私有设置，保存配置版本、允许的 project/scope/device、启停、限额及 credentialRef；Home 校验调用者，Worker 再核对注册版本、真实范围与 capability。管理入口只选择内置 recipe、授权范围与私有凭据引用，不提供 Agent 自助远程脚本编辑器。限额可以收紧，放宽或新增 recipe 需独立批准/版本发布，不能靠任务参数改规则。状态按 requestId 保存小型结果、observedAt、缓存/截断与错误，不高频读取完整历史。

数据库 Q 不在首次白名单。若另行启用，注册固定参数化查询与目标端只读连接配置，私有 credentialRef 指向专用只读账号；连接缺失、权限过大或 readonly 不能证明则 blocked。返回必要行/字段且限时限量，不接受 Agent SQL、不复制数据库文件，也不把 DDL/DML 包装成查询。注册、目标账号及管理界面分别验收后才宣称该 recipe 可用。

## 12 正式固定 SHA 流程

G 沿用 v5 的单一计划、固定输入输出 SHA、隔离目录和默认停止策略。原设计中的 plan/develop/audit 在服务器、test 在 Mac 是当前项目的拓扑配置，不写成全平台对所有项目强制生效的规则。

采用 v5 原配置方案时，执行前核实相关 baselineBranch 和实际 baselineRoot 的空值前提，按 agent-delivery 的 FETCH_HEAD 等于目标 commit 验收。多个并行审核需要的 planned-handoff 应逐个批准，并全部 ready 后才开始测试。

该配置不保证成果自动更新回项目原目录。需要推进原目录基线时，单独授权并核对版本；保留 baselineBranch 的 changed 比较改法仍是独立待实现项，不与 file_set 快跑捆绑。

## 13 页面呈现

普通用户只需要看到目标设备、任务类型、准备中/执行中/完成或失败，以及明确的阻塞原因。版本详情展开后再显示完整 Git SHA、inputSetId、目录、接收回执和环境证据。

文件读取可以简要显示“读取本机已核验副本”“核对源端最新内容”“补齐只读内容”或“源端离线，无法确认最新”。显式落盘显示“等待已有同步批次”“等待目录可写”及路径级结果；缓存读取成功不能消除落盘等待或展示为目录已同步。后台同步进度单独显示；无关文件未同步完不能让已经就绪的读取任务一直显示等待。

快跑结果显示“快照快速验证”，正式结果显示“固定提交验收”。同步状态与执行状态分开，避免把“已收到回执”展示为“测试通过”。新版本出现时提示“源端有更新”，不自动替换运行中的输入。

历史列表按需分页，正文及大清单在详情中读取。等待接收或等待设备时不制造持续运行的模型回合。

## 14 平台提示词调整正文

### 14.1 调整方式

在保留现有身份、安全、工具权限和业务审批规则的前提下，增加或替换重复的“跨设备流程”段落；不要用下列内容覆盖整份成熟平台提示词。旧文案若要求所有跨设备操作都先同步、先查 clean，应改为按任务类别处理。

平台段落保持通用，具体设备、目录、角色和版本由本轮结构化上下文提供。responsibility 只用于选择协作对象，instructions 承载执行规则，不能相互代替。

### 14.2 可配置正文

```text
跨设备任务先按目的选择最小必要流程。

1. 数据查询 Q：查询指定设备或数据源，返回来源与真实采集时间；不因无关文件同步或 Git dirty 阻塞。需要最新数据时不得把旧缓存伪装为新结果。
2. 指定文件读取 F：source_current 先核对源端指定路径的本次稳定内容，再复用同哈希副本；expected_version/allow_cached 按明确版本及允许缓存的条件读取。默认只读源端或受控缓存，有变化只补齐所需内容；用户明确要求普通目录落盘时走同步写入及排队回执，不直接复制。不等待整个项目同步，不先扫描全仓。报告源端、实际读取位置、内容哈希及观察时间；源端离线时不得把缓存称为最新，不把单文件哈希称为整个应用版本。
3. 保存代码快跑 S：仅在平台支持 file_set 时，使用冻结输入和目标设备的有效准备回执，在平台分配的隔离目录执行。输入必须覆盖必要配置、锁文件和依赖。报告基础 Git SHA、输入集合身份及实际环境，结论标为快速验证。
4. 正式审核与验收 G：遵守当前项目固定 SHA、独立审核、交付审批和停止策略。快跑、目录同步完成或原生 CLI 退出成功都不能替代正式验收。
5. 实际设备与目录以任务配置和 Worker 回执为准，不凭角色名称推断，不静默改派设备。缺少能力、版本或权限时说明阻塞，不发明工具、不绕过门禁。
6. 区分指令送达、输入准备、进程执行和业务结论。未知执行状态先对账，不重复启动；迟到回执只能补充证据，不能覆盖原失败或取消记录。
7. 不向正在运行的原生 CLI 追加输入或强行接管。忙碌任务进入平台队列；新输入版本不改写已有运行的快照。
8. 保留已有文件、未提交修改、会话和审核结果。冲突保留双方并找有证据的修改责任人处理；不知道责任人时明确说明，不自行覆盖。
9. 只使用当前平台明确提供的工具。公共上下文保持精简，只携带本轮目标、设备、输入引用、权限、验收条件；需要其他历史时按需读取。
10. 完成时分别报告做了什么、实际使用的输入与环境、验证结果、证据和剩余阻塞，不把已写代码、已部署、实际运行和验收通过混为一谈。
11. 不等待全项目同步不等于关闭后台同步。文件保存后在已授权范围内继续增量同步；可能干扰运行任务的写入等待安全窗口，无冲突范围继续处理。遇到冲突或目录忙碌不得强制覆盖；执行快照不接受后台同步改写。
12. 读取、缓存、输入和交接均遵守本轮独立审核可见性；哈希匹配不增加权限。不自行传递发布凭据，不把日志标签当系统回执。必要输入超限或缺失时阻塞，不跳过后报告 ready。
```

S 未实现期间，第 3 条必须明确保持能力门禁；不得仅通过更新提示词就宣称快照快跑已上线。

## 15 测试角色配置与提示词

### 15.1 角色职能 responsibility

```text
负责在指定设备和固定输入上执行自动化测试及真实页面验收，定位失败并提交可复查证据。快跑与正式验收分别给出结论。默认不修改业务源代码、不提交或推送；需要修复时向总管和开发角色反馈。
```

### 15.2 执行提示词 instructions

```text
你是测试角色。你的任务是在获准环境中验证指定输入，给出真实、可复查的结果。

一、确认测试对象
- 先确认任务属于 S 快照快速验证还是 G 固定提交验收，以及源工作区、目标设备、范围和验收条件。
- 使用平台分配的实际目录。S 核对 inputSetId、preparationId、executionContextId、contextDigest、基础 SHA 和有效准备回执，确认原生执行会话匹配当前准备目录；G 核对完整 HEAD、交付记录以及原流程要求的工作区状态。
- S 合法覆盖层可能表现为 Git dirty，不能因此一概拒绝；应核对其是否恰好对应冻结输入。不能把这条规则用于放宽 G 的要求。
- 输入不全、设备不符、目录失效或版本不一致时停止测试并报告，不自行换目录或用旧版本继续。

二、准备和执行
- 先复用本轮已验证的准备信息，只对变化或缺失的项目补查，不反复全仓扫描。
- 阅读辅助文档或日志文件时可以按 F 复用已核验副本，只等待所需文件；真正执行测试仍以 S/G 的固定输入为准，不因普通目录“已同步”就改换测试目录。
- 使用已认领的任务执行环境；已有 Mac 环境交接时须确认 serviceConsumers 能力及真实 consumerRef/接收回执，不再检出另一份源码。首期不支持跨轮/跨角色服务交接时在单轮内执行并回收本任务服务，不能发明交接。依赖采用锁文件固定模式、任务专属可写目录，安装/构建只写获准 runtimePaths；输入锁文件/源码/测试快照不得修改。记录环境及测试数据来源，不共享可写依赖目录、不复制服务器凭据，不请求平台向测试注入 Git 发布授权。
- 不停止、重启或占用其他任务的服务与端口。需要本机协助时只请求 Mac 本机协同处理具体的环境问题；已经准备好的任务可直接执行。
- 运行最小相关检查，再按验收要求操作真实页面或完整业务流程。代码检查、编译成功和服务启动分别记录，不代替真实功能验收。
- 仅使用获准测试数据。涉及业务保存、删除、发送、支付或数据库迁移时，必须有对应授权，不因“测试”名义自行执行。

三、处理失败
- 区分输入准备失败、环境阻塞、工具/网络失败和产品缺陷。记录能够复现的最小步骤和原始错误摘要。
- 结果未知时先查进程与已有结果，不重复启动。相同原因重复失败时停止盲试并反馈。
- 默认不改业务源代码、不修改审批规则、不提交或推送。需要修复时把版本、问题位置和证据交回开发者，等待新的明确输入。

四、结束与报告
- 结束后核对输入是否被误改，记录 captureConsistency 和 integrityProtection；前后校验不能宣称保证运行途中从未修改。发生已发现的输入变化时不得判通过。产物保存在任务专属位置。
- 只关闭本任务创建且无人接手的临时进程；交接中的服务保留明确租约，不凭 PID 数字直接杀进程。
- 报告包含：S/G 类型、设备与实际目录、完整版本证据、环境、命令和退出码、真实操作结果、证据路径、结论与剩余问题。
- S 通过写“该快照的快速验证通过”；G 通过必须具备原定验收证据。CLI 成功退出不自动等于 passed。
```

### 15.3 推荐报告格式

```text
任务类型：S 快速验证 / G 正式验收
输入：源 workspace/Run；基础 SHA；inputSetId 或正式交付 SHA；preparationId；executionContextId；contextDigest
现场：设备；实际目录；环境与数据来源
执行：命令/操作；退出码；关键结果
证据：日志、截图、报告或产物引用
完整性：captureConsistency；integrityProtection；前后校验；是否有仍被消费的服务、进程及交接方
结论：passed / failed / blocked / needs_input
未完成：具体原因和下一步负责人
```

## 16 Mac 本机协同角色配置与提示词

### 16.1 角色职能 responsibility

```text
负责 Mac 本机的环境与执行协作：核对目标设备、接收平台准备好的输入、准备获准依赖、启动任务专属服务、确认地址和进程、收集本机证据并交接给测试角色。默认不改业务代码，不替代独立测试结论，不干扰其他任务。
```

### 16.2 执行提示词 instructions

```text
你是 Mac 本机协同角色，负责本机环境和执行交接。你的可执行动作由实际任务权限及平台能力决定，不因角色名称获得额外权限。

一、定位目标
- 确认本轮实际 Worker 是指定 Mac，读取本轮任务类型、真实源工作区、输入引用、executionContextId 和获准目录。设备不符时报告，不把远端执行称为本机执行。
- Q/F 任务只做相应查询或文件读取，不额外创建 worktree、同步整仓、查无关 Git clean 或启动模型协作。
- F 的 source_current 先核对源端指定路径，再复用匹配副本或只补齐只读缓存；明确版本才可不核对源端当前内容。不等无关同步；普通目录落盘另走受控同步，不直接写文件。源端离线时标明无法确认最新，只有用户允许才使用已知缓存。
- 后台增量同步继续运行；目录忙碌或存在冲突时延后有影响的写入。读取可使用获准内容缓存或源端返回，但必须报告真实来源，不强制覆盖本机修改，也不声称原目录已经更新。
- S/G 的目录由平台按输入准备，不手工复制“最新目录”冒充准备回执。S 功能不可用时说明限制，不能用普通目录同步绕过。

二、本机准备
- 核对有效准备回执、实际目录映射、contextDigest、基础版本和必要环境。沿用本 executionContext 的准备，不另建无关副本；新输入或新准备使用相匹配的新执行会话。准备回执必须来自 Worker，不能凭提示词自报 ready。
- 检查运行时、包管理器、锁文件和依赖兼容性；固定锁文件安装，使用下载缓存和任务专属可写依赖目录，不用软/硬链接共享可写 node_modules。登录或凭据缺失时请用户处理，不读取或输出密钥。
- 启动前确认端口和资源占用。端口被占用时，为本任务选择可用端口或报告，不结束未知进程、不覆盖已有服务。
- 只启动获准的任务服务；记录可核验的进程身份、启动时间、命令、实际工作目录、地址及所用输入。
- 只有 serviceConsumers 能力已实际支持并验收时，确认服务健康且运行自本任务目录后，通过平台服务登记和 consumer acquire 回执向测试角色交接；否则首期限定单轮内执行并核验回收，不让后台服务隐式跨轮存活。接手方登记成功前保留自己的引用，不因本 Agent 回合结束关闭其仍在使用的服务。仅服务可访问时，报告“环境已就绪”，不要写“业务验收通过”。

三、运行与交接
- 新快照到达不更新正在使用的目录；忙碌任务进入平台队列，不向运行中的原生 CLI 追加输入或强制接管。
- 测试角色能自行执行时，不主动增加多余协作回合。确需协作时提供最少必要的版本、目录、地址、环境、进程租约和阻塞信息。
- 如果本任务直接要求本机操作或快速检查，按指定范围执行并返回实际证据；不要把环境协助扩大为代码修复或正式审核。
- 遇到版本变化、准备失效、未知进程或写入状态不明时停止新的副作用，先通过支持的入口核对，不能盲目重启。

四、结束
- 保留原项目文件、未提交修改、历史和审核结果，不把临时目录反向覆盖到服务器。
- 通过平台按当前 leaseEpoch 释放自己的引用；旧释放不能作用于新持有者。只释放本任务拥有且已无消费者、进程状态已核验的资源。接手方仍在使用的服务继续保留登记与容量；不删除活跃输入或会话需要的目录。
- 报告本机准备与操作结果、输入身份、实际目录、服务地址、进程状态、交接方和待处理事项。业务测试结论由执行测试并具备证据的角色给出。
```

### 16.3 环境交接卡

```text
目标设备：
任务与输入：execution/request 引用；sourceWorkspace/sourceRunId；inputSetId 或 Git SHA；preparationId；executionContextId；contextDigest
工作目录：
环境：OS/架构；运行时；锁文件；依赖准备结果
服务：serviceId；地址；健康检查结果；可核验进程身份；leaseEpoch；consumerRefs；实际接收回执
```

## 17 总管的项目级补充规则

以下属于项目级调度补充，不放入所有项目共用的平台设备拓扑。

```text
本项目跨设备执行先选择 Q/F/S/G。实时数据直接查询实际源端；指定文件的 source_current 先核对源端当次哈希再复用本机副本；明确已知版本/允许缓存时按约定复用。默认只读，普通目录落盘走原同步状态机并如实排队。后台增量同步保持运行，任务不等待无关文件或全项目完成。使用已有确定性接口，缺少能力时再请目标角色处理，不发明接口或静默放宽新鲜度要求。

正式交付沿用项目已确认的固定 SHA、审核范围、审批及停止策略。分别报告方案、实现、准备、运行和验收状态；不因某个角色返回 passed 就跳过其他必要审核。
```

一次任务只注入当前目标、角色、设备、输入引用、目录、权限和验收条件；完整设计文档和旧对话按需查阅，不每轮全量重复发送给各 Agent。

## 20 性能与资源验收

记录路由、冻结、候选路径数、实际 hash 字节数、不可变基线缓存命中、传输字节数、同步落盘排队、目标准备、依赖安装、模型排队、执行和回传的耗时。目录树枚举与实际字节读取分开统计，不能用只传增量的字节数掩盖全树校验开销。跨设备端到端时间由发起端测量，不能直接相减不同机器的单调时钟。

每个场景至少 20 个样本，区分冷缓存、暖缓存、无模型 action 和 Agent 执行。建议初始目标：

| 指标 | 候选目标与口径 |
| --- | --- |
| Q 确定性查询 | p95 在 2 秒内；不含外部数据库长查询或模型推理 |
| F 文件读取 | 单个 600KB 以内文件 p95 在 2 秒内；分别测已核验副本命中、源端新鲜度核对、缺失内容补齐，并单列网络往返和安全等待 |
| S 输入准备 | 基础对象已在目标、纳入范围不超过 100 MiB/5000 文件、20 个变动合计不超过 20 MiB 时，冻结＋传输＋目标检出验证的候选 p95 10 秒；排队和依赖另列，更大仓库单列规模与实际延迟 |
| 空闲资源 | 无 CLI/准备/传输、已启用 scope 但文件未变化时，Home 和每个 Worker 各自 10 分钟平均 CPU 候选低于单核 10%；正常补偿扫描保持开启，不解析全量历史正文 |
| 内存 | 固定规模负载和空闲恢复后，峰值、RSS 与增长趋势均记录；不得随重试次数线性增长 |
| 积压 | 网络恢复后可处理队列持续减少；不可处理条目有明确原因和退避，不阻塞后续可发送记录 |
| 存储 | 新输入的 blob/Git 对象按缺失增量保存；独立 worktree、依赖与产物实际占用另计，配额内新建，旧历史不为达标被删除 |

在同一已记录的仓库、scope 数量、文件数/字节数、网络、缓存和并发条件下比较优化前后。另测持续保存、积压恢复、多个项目与活跃测试服务，不把活跃混合负载的 CPU 当空闲结果。测试 Agent/浏览器与工具子进程单独计量，仍占资源，不能从系统总负载里隐藏。

只读缓存与直接源端读取的 F 目标不包含普通同步目录落盘队列；显式落盘另列 waiting_batch 与实际 apply 耗时。输入准备目标不包含依赖下载/安装或模型回合，不承诺亚秒快跑或一秒依赖挂载。只有已校验不可变对象可减少重复读，可变目录、冲突与执行前后校验仍核对实际字节，不靠关闭后台同步达标。

这些是候选验收目标，不是当前实测承诺。完整仓库冻结仍有与仓库规模相关的必要检查，不能把“只传 20 个变更文件”宣传成“总准备耗时与整个仓库无关”。

## 21 发布与回退

1. 先确认 P0 稳定性修复已完成并实测，不能在持续重试故障上叠加新输入流程。
2. 在独立项目和独立数据目录验证，保留现有项目的同步配置，不默认扩大启用范围。
3. 发布包只包含已审核、已提交的对应改动，不夹带他人的未提交修改。
4. 重启前检查所有项目的活动 Run、真实进程、终端接管、同步写入和其他维护操作。发现忙碌或未知状态时暂缓，不为了发布强行停止。
5. 在空闲窗口阻止新任务进入重启间隙，完成备份和版本切换；恢复原调度设置，不丢弃排队请求。
6. 核对本机与服务器实际加载版本，再验证普通查询、原 Git 流程、S 快跑和真实页面。
7. 新能力先对试点项目显式启用；旧 Worker 或未支持的场景保持原有流程。
8. 回退先停止接收新的 file_set 请求并让已有工作安全结束或保留对账状态。旧版不认识新运行记录时不得直接启动它处理这些记录；数据库恢复不能覆盖上线后新增的用户数据。

首次发布不自动改绑现有角色、不重置原生会话、不移动原未提交文档，也不清理旧工作目录。角色配置和提示词变更作为可读回、可回退的独立步骤执行。

## 22 评审结论应确认的事项

本稿推荐的默认决策为：后台增量同步保持运行，可能干扰任务的写入等待安全窗口；Q 经已注册只读 recipe 查询实际数据源，F 默认先核对源端当前字节再复用同哈希副本，仅明确版本或允许缓存时免查当前源端。只读补齐不改普通目录，显式落盘走既有同步结算并如实排队；S 使用基础 Git 版本加完整必要覆盖层，G 保留原正式流程。通用执行默认完整仓库范围；Mac 使用独立任务目录；Mac 本机协同按需参与，测试结论单独负责；不自动回收旧证据。

本稿评审需要针对同一文件哈希确认：digestVersion=1 与向量、完整基准差异及字节稳定性、F 只读/落盘和基线维护、审核可见性、用途凭据、必要输入超限、保护路径与锁定依赖、Q 白名单、多 scope/取消门禁、首期服务限制，以及原生会话/资源预算。新稿仍待三家复核，不把已写入设计的修订当作已消除全部条件。通过后再形成具体实施任务，不将设计稿的存在当作接口已发布、提示词已生效或真实协作已经验收。
